# Befehle

`basalt` ohne Unterbefehl startet `chat`.

| Befehl | Funktion |
|---|---|
| `basalt onboard` | Einrichtungsassistent für den ersten Start: wählt ein passendes Modell für Ihren Rechner aus und lädt es herunter |
| `basalt fit` | liest die Hardware aus und bewertet den Modellkatalog anhand der verfügbaren Ressourcen |
| `basalt chat --model <id>` | interaktiver Terminal-Chat |
| `basalt serve --model <id> --rest` | REST-Server auf :8080 (OpenAI- + Anthropic-kompatibel) |
| `basalt serve --model <id> --mcp` | MCP-stdio-Server für Claude Desktop / Cursor |
| `basalt serve --model <id> --stats` | gibt alle 5 s Telemetrie auf `stderr` aus (`--stats-interval`); dieselben Werte unter `GET /api/v1/stats` und in MCP `status` |
| `basalt serve --model <id> --canary-minutes 30` | sendet alle 30 Min. im Leerlauf eine Anfrage mit bekannter Antwort bei Hintergrundpriorität; Bestanden/Fehlgeschlagen, Zähler für degenerierte Ausgaben sowie Drift pro Modell bei tok/s und Draft-Akzeptanzrate stehen unter `health` in `GET /api/v1/stats` (#325) |
| `basalt models list --author <org>` | Modelle eines HuggingFace-Autors durchsuchen |
| `basalt models download <repo-id>` | in den gemeinsamen HF-Cache herunterladen |
| `basalt models info <repo-id>` | Größe, Quantisierung, Kontextfenster |
| `basalt models cache` | was auf der Festplatte liegt und wie viel Speicherplatz es belegt |
| `basalt models check <repo-id>` | prüft, ob das Modell in den Speicher passt (Exit-Code ungleich null, falls nicht) |
| `basalt models check --deep <repo-id>` | außerdem vor dem Download: lädt nur die Safetensors-Header (wenige hundert KB), baut das Modell rein formbasiert dagegen auf und rendert das Chat-Template; listet fehlende, unerwartete oder falsch geformte Tensoren, einen nicht unterstützten `model_type` oder einen Template-Fehler auf und beendet sich mit einem Exit-Code ungleich null |
| `basalt models inspect <repo-id>` | überprüft, ob ein zwischengespeichertes Modell vollständig ist, und misst seine reale Bitbreite |
| `basalt models inspect --verify <repo-id>` | berechnet außerdem den Hash jeder zwischengespeicherten Datei neu gegen ihren Sidecar oder den Digest des Hubs: `true`, `false` oder `unknown` pro Datei, schreibgeschützt (#367) |
| `basalt models distill <model> --prompts FILE --teacher-url URL --teacher-model NAME` | destilliert ein Teacher-Modell hinter einer API im OpenAI- oder Anthropic-Format (`--provider`) in ein LoRA für das lokale Modell; der Key stammt aus `BASALT_TEACHER_API_KEY` mit `BASALT_TEACHER_URL`; `--budget-usd` stoppt vor Überschreiten eines Budgets, `--filter verify` behält nur Antworten, die mit dem `answer`-Feld des Prompts übereinstimmen, `--on-policy` lässt das Student-Modell samplen, während ein Basalt-Teacher mit demselben Tokenizer dessen Tokens über `/v1/score` bewertet (Reverse-KL pro Token), Offline-Läufe speichern alle `--checkpoint-every` Schritte einen Checkpoint und setzen mit `--resume` fort (#393) |
| `basalt models train-jepa <model> --dataset FILE` | trainiert einen JEPA-LoRA-Adapter und Projektor auf einem Multi-View-Datensatz (eine Szene pro JSONL-Zeile, mindestens zwei Views); gibt den Loss und den Embedding-Rang vorher und nachher aus |
| `basalt models convert <source> --out DIR` | Universeller Any-to-Any-Konverter (#546): Requantisierung über `--to macaq:affine|mxfp4|moe` (Block-Walsh–Hadamard + Hessian-Flip-Refinement, routergewichtetes 2.8 bpw MoE #599), `--to flatquant` / `--to lirquant` (#594), `--to sinq` / `a-sinq` / `eaquant` (#561), `--to e8p` (`QuIP#` 2-Bit-Gitter + `TurboBoA` Babai–LLL, #589), `--experimental-qtip 2.0\|2.5\|3.0` (#494), `nf4`, `SVD-LLM V2` / `OBR` (#592), native `.gguf`-i-Quants & `MACaQ-R`, sowie `--pv-tune` (`--pv-preset fast|full`, #545), domänenbewusstes QAT-STE-Refinement und Post-Quantisierungs-Audit für Qualität/Fairness/Leakage (`#623`). Auch über REST `/v1/models/convert*` und macOS `ConvertModelSheet` verfügbar |
| `basalt serve --video-model <id> --rest` | Stellt das gestaffelte 24-GB-UMA-Video-Studio (`LTX-2.5 AV-DiT`, `Kandinsky 6.0`, `LingBot-Video MoE`, `Wan 2.2`) über `/v1/videos/*` mit kausalem 3D-VAE, STA-Metal-Kernel und `AVAssetWriter`-`.mp4`-Muxing bereit (#608–#611, #614) |
| `basalt review --diff FILE\|- --model <id>` | überprüft einen Diff mit dem lokalen Modell; `--gitlab` / `--gitea URL --repo R --number N` laden stattdessen einen Merge Request, `--post` veröffentlicht das Review zurück (`GITLAB_TOKEN` / `GITEA_TOKEN`) (#35) |
| `basalt compose` | startet, plant, vergleicht (`diff`), lädt (`pull`) oder stoppt ein YAML-System mit mehreren Modellen (`models`, `pipeline`, `pipelines`, `experimental`, `mcp`, `variables`, `profiles`); lädt Modelle, Pipelines, Budgets und laufende `experimental`-Einstellungen (`speech_analyzer`, `image_fallback`, `telemetry_confidence_every`, `adaptive_thinking_budget`) im laufenden Betrieb über `/v1/compose/apply` neu (#412, #423, #485) |
| `basalt cloud configure` | OpenRouter-Fallback für alles, was lokal nicht passt |
| `basalt cloud cost` | bisherige Ausgaben für den Cloud-Fallback |

Innerhalb von `basalt chat`:

| Eingabe | Wirkung |
|---|---|
| `/clear` | leert die Konversation und den Bildschirm |
| `/color`, `/theme` | schaltet das Farbschema des Terminals durch |
| `exit`, `quit` | beendet den Chat (ohne Schrägstrich) |

Die wichtigsten Flags für `serve`:

| Flag | Wofür es gedacht ist |
|---|---|
| `--reasoning-effort none` | verhindert, dass ein Reasoning-Modell das gesamte Budget innerhalb von `<think>` verbraucht |
| `--reasoning-effort xhigh\|medium\|low` | Thinking-Budget für die Qwen-Familie |
| `--quant 4bit` | wählt einen Quantisierungs-Unterordner in Repositories, die mehrere Varianten mitliefern |
| `--kv-bits 4\|8\|auto` | quantisiert den KV-Cache — schafft auf Rechnern mit knappem Speicher Platz für die Generierung; deaktiviert die Wiederverwendung des Prompt-Caches. MLX führt den Prefill des Prompts in fp16 aus und quantisiert ihn danach, sodass der Prompt selbst nicht länger als in fp16 sein darf (kürzer, da bei der Konvertierung kurzzeitig beide Kopien im Speicher liegen). `auto` bleibt bei fp16 samt Prompt-Cache-Wiederverwendung, bis Prompt plus `max_tokens` einer Anfrage nicht mehr passen, und führt diese Anfrage dann mit 8 oder sonst 4 Bit aus |
| `--kv-bits turbo3\|turbo4\|turbo8v4` | **Experimentell** (#471): der TurboQuant-Cache dieses Forks auf Full-Attention-Layern (Rotation, Lloyd–Max-Codebook, eine Norm pro Vektor; die ersten und letzten beiden geeigneten Layer bleiben 8-Bit-affin). Nicht kombinierbar mit `--kv-zones`. Gemessen auf M4 Pro bei 8k Kontext gegenüber 4-Bit-affin: Decode 8–13% langsamer (Qwen3.8-27B 13.8 vs. 15.0 tok/s, LFM2.5-24B 82 vs. 94); Decode-Perplexität über 384 Tokens +0.3% / +1.3% gegenüber +1.5% für 4-Bit bei Qwen3.8, +10.1% / +3.6% gegenüber +5.0% bei LFM2.5; KV bei 16k nicht kleiner (Qwen3.8 460 / 511 MB gegenüber 461, LFM2.5 118 / 131 gegenüber 97, Gemma 4 26B-A4B 423 gegenüber 306). Kompression greift im Decode: ein Multi-Token-Chunk liest die rohen Keys |
| `--kv-bits polar4` | **Experimentell** (#351), mit `--kv-zones`: der zonierte Mittelteil speichert jedes RoPE-Paar des Keys als ein Byte (5-Bit-Phase, 3-Bit-Modulus auf Rayleigh-Quantilen, skaliert pro Head und Paar anhand des ersten Migrations-Batches) und die übrigen Dimensionen 4-Bit-affin; Values bleiben 4-Bit-affin. Nur Qwen3, Qwen3.5 und LFM2, deren RoPE die Dimensionen i und i + d/2 paart; jedes andere Modell behält affine Keys bei und protokolliert dies. Gemessen auf M4 Pro, 256 Tokens nach 8k dekodiert, gegenüber zoniertem q4 und k8v4: Perplexität Qwen3.8-27B 8.61 vs. 8.56 / 8.50, LFM2.5-24B 61.2 vs. 76.5 / 70.9 (eine verrauschte 256-Token-Stichprobe); zoniertes KV 196 vs. 197 / 255 MB und 59 vs. 62 / 80 MB; Decode 12.4 vs. 14.0 / 14.6 tok/s und 11.3 vs. 19.5 / 18.2 (der Mittelteil wird in jedem Schritt zu fp16 dekodiert, es gibt keinen Polar-Kernel); ein 16k-Passkey wurde bei den Tiefen 0.2 und 0.8 auf beiden Modellen gefunden. Im Offline-Test schnitt Polar bei gleicher Bitbreite nicht besser ab als affin |
| `--kv-bits k8v4` | mit `--kv-zones`: der quantisierte Mittelteil speichert Keys mit 8 Bit und Values mit 4 Bit (13 Bit pro K+V-Paar mit Gruppen-Scales, 0.41× fp16, zwischen 0.53× bei 8-Bit und 0.28× bei 4-Bit). `auto` mit `--kv-zones` probiert diese Stufe zwischen 8 und 4 Bit. Bei einem Modell, für das Zonen nicht greifen (Gemma 4), läuft es als einheitliches 8-Bit. **Experimentell:** `k8v4h` wendet vor der 4-Bit-Quantisierung zusätzlich eine Walsh–Hadamard-Transformation auf die Values an (und beim Lesen deren Inverse), um Ausreißer-Kanäle zu verteilen; dies ist strikt opt-in, `auto` wählt es nie automatisch. Gemessen mit 8k Tokens nach einem 8k-Kontext, Perplexität gegenüber `k8v4`: Qwen3-4B 6.568 vs. 6.562, Ornith-1.5-9B 4.937 vs. 4.920, LFM2.5-8B 8.723 vs. 8.750 (je ein Lauf, im Rahmen des Rauschens), und der Spitzenspeicher nach einem 16k-Prompt stieg um etwa 85 MB bei Ornith und 30–150 MB bei Qwen3-4B (die fp32-Kopie der rotierten Values). Rotiert werden Head-Dimensionen 2^k und 12·2^k, bei denen die Transformation von MLX ihre eigene Inverse ist; andere Head-Dimensionen bleiben unrotiert, und `serve` protokolliert das beim Laden. Bei längeren Kontexten (32k+) oder Modellen mit Ausreißer-Kanälen in V könnte dies relevant sein; das ist ungetestet |
| `--kv-zones` | mit `--kv-bits`: hält die ersten 64 und die letzten 1024 Tokens jedes Full-Attention-Layers in fp16 und quantisiert nur die Tokens dazwischen bereits während des Prompt-Prefills. Da kein fp16-Prefill nachträglich konvertiert werden muss, kann der Prompt den gesamten quantisierten Speicherplatz nutzen und der Spitzenspeicher sinkt; bei Qwen3-4B, 8k Tokens nach 8k Kontext bewertet, liegt die 4-Bit-Perplexität bei 6.58 gegenüber fp16 6.56 und einheitlichem 4-Bit 8.66 |
| `--kv-evict F` | **Experimentell**, mit `--kv-zones`: verwirft den Anteil `F` (0–0.9) des quantisierten Mittelteils jedes Full-Attention-Layers, sobald Tokens das aktuelle Fenster verlassen — pro KV-Head diejenigen, deren Keys die größte L2-Norm aufweisen (arXiv:2406.11430). Benötigt keine Attention-Gewichte, sodass Attention auf den fusionierten Kernels bleibt; Sinks und das aktuelle Fenster werden nie verworfen, und der von `serve` sowie `models check` gemeldete Platz zählt nur die behaltenen Tokens. Nach einem 16k-Prompt mit k8v4 sinkt KV bei Qwen3-4B von 1.11 GB auf 0.89 GB bei 0.25 und 0.66 GB bei 0.5. Dies geht zulasten der Qualität: Perplexität (8k nach 8k bewertet) 6.71 / 7.04 gegenüber 6.56 bei Qwen3-4B, 9.06 / 9.52 gegenüber 8.75 bei LFM2.5-8B, unverändert bei Ornith-1.5-9B; ein 16k-Passkey ging bei 0.25 in einer von fünf Tiefen bei Qwen3-4B und Ornith verloren, und die Greedy-Ausgabe weicht bereits in den ersten Tokens von fp16 ab. Gemma 4 sowie Modelle, die in einem Durchgang mehr als das aktuelle Fenster prefillen (beim Laden geprüft), behalten alle Tokens und werden entsprechend dimensioniert |
| `--kv-head-split R` | **Experimentell**, nicht mit einheitlichem `--kv-bits`: behält den gesamten Kontext nur in dem Anteil `R` (0.05–1) der KV-Heads, die Fakten aus der Mitte eines langen Prompts lesen, einmalig pro Modell auf einem synthetischen Passkey-Set bewertet (DuoAttention, zwischengespeichert in `~/.basalt/head-scores`); die übrigen Heads behalten 128 Sink- und 256 aktuelle Tokens. Bei Qwen3-4B bei 32k mit `R` 0.25: KV 4.76 → 1.26 GB, Decode 27.2 → 36.2 tok/s, Passkey 10/10 bei 16k und 32k. Wird mit einer Warnung abgelehnt bei der Qwen3.5-Familie, LFM2-/Nemotron-H-Hybriden sowie Modellen, deren Attention nicht über den Cache läuft (Gemma 4). Bei den Hybriden verlor die durch Ablation gewählte 25-%-Auswahl den Passkey bei 16k (Qwen3.8-27B 0/3 Tiefen, LFM2.5-24B 2/3) und erhöhte die Perplexität um 24% bzw. 42%; die Auswahl der Heads nach Ausgabetreue ist #282. Mit `--kv-zones --kv-bits k8v4` (experimentell, aus, sofern nicht beide angegeben sind) speichern die behaltenen Heads ihren langen Kontext zoniert: exakt die ersten 64 und letzten 1024 Tokens, den Mittelteil mit 8-Bit-Keys und 4-Bit-Values; die übrigen Heads verbleiben wie oben. Wie `--kv-zones` gilt dies nur für Anfragen ohne Prompt-Cache-Namespace |
| `--prompt-cache-mb N` | Speicher, der für den Präfixbaum des Prompt-Caches reserviert wird (Standard: die Hälfte dessen, was Metals empfohlenes GPU-Working-Set nach den Gewichten übrig lässt, beim Laden protokolliert; `0` deaktiviert), siehe unten |
| `--prompt-cache-disk-mb N` | speichert den Prompt-Cache beim geordneten Herunterfahren, vor einem Modellwechsel und beim Beenden von `basalt chat` unter `~/.basalt/prompt-cache/` (`--prompt-cache-dir`), sodass eine fortgesetzte Sitzung oder ein neu gestarteter Server sein Präfix von der Platte wiederherstellt, statt es neu zu prefillen (Standard `0`, aus). Die am häufigsten genutzten Zweige werden zuerst geschrieben, bis zu `N` MB und nur diejenigen, deren Schreibvorgang bei angenommenen 1 GB/s in das Zeitlimit beim Herunterfahren passt; ein längerer Pfad derselben Konversation ersetzt die kürzeren Dateien, die er abdeckt, die am längsten nicht verwendeten Dateien werden gelöscht, um Platz zu schaffen, Dateien, die länger als `--prompt-cache-disk-days` (7) ungenutzt waren, werden beim Start entfernt, und `basalt sessions prune` erledigt dasselbe offline. Das Verzeichnis muss neu, leer oder ein früheres Prompt-Cache-Verzeichnis sein (ein Verzeichnis mit anderen Dateien wird abgelehnt). Eine Datei wird nur von demselben Modell (Gewichts-Blobs oder stichprobenartig geprüfter Gewichtsinhalt außerhalb des HF-Caches, Konfiguration, Tokenizer und Chat-Template), derselben Basalt-Version und demselben Cache-Format verwendet; alles andere, eine abgeschnittene Datei oder ein anderes Layer-Layout fällt auf einen normalen Prefill zurück. Benötigt `--session-log full` (die Dateien speichern die Konversation als KV-Tensoren) und den In-Memory-Prompt-Cache; `--kv-bits`, `--kv-zones` und multimodale Prompts werden nie persistiert |
| `--cache-blend` | verwendet zwischengespeicherte Prompt-Chunks in beliebiger Reihenfolge approximativ wieder (CacheBlend); `--cache-blend-ratio R` legt den neu berechneten Anteil fest (Standard 0.3), siehe unten |
| `--min-p`, `--top-k`, `--seed` | Sampling; `--seed` macht einen nicht-greedy Lauf reproduzierbar; ein `min_p` in der Anfrage überschreibt `--min-p` |
| `--max-tokens` | Standardobergrenze für die Generierung (2048–128000) |
| `--dry-run` | Speicher-Machbarkeitsprüfung, danach Beendigung ohne Laden |
| `--config basalt.yaml` | Server-Optionen aus einer YAML-Datei: Schlüssel unter `defaults.{model,serve,mcp}` werden zu den entsprechenden Flags, Kommandozeilen-Flags haben Vorrang, unbekannte Schlüssel werden mit Zeile und Spalte gemeldet (#344) |
| `--mcp-enable <tool\|group>`, `--mcp-disable <tool\|group>` | aktiviert oder deaktiviert bei `--mcp` gezielt einzelne MCP-Tools oder Gruppen (`serving`, `gemma`, `media`, `harness`, `xray`, `surgery`, `research`, `all`), ohne die gesamte `--research-tools`-Oberfläche freizugeben; `--mcp-disable` sticht immer `--mcp-enable` und `--research-tools`, und unbekannte Namen schlagen beim Start sofort fehl. Auch als `defaults.mcp.enable` / `defaults.mcp.disable` in `basalt.yaml` (#484) |
| `--adapter name=dir` | lädt einen mlx-lm-LoRA-Adapter auf das geladene Basismodell (wiederholbar); eine Anfrage wählt ihn über `X-Basalt-Adapter: name`. Anfragen für denselben Adapter laufen gemeinsam, ein Wechsel wartet auf laufende Generierungen, jeder Adapter hat seinen eigenen Prompt-Cache-Namespace; ein Adapter, dessen Tensoren zu keinem Layer der Basis passen, wird beim Start abgelehnt (#179) |
| `--experimental-zero-copy-body` | **Experimentell**: verpackt jeden REST-Anfragekörper ohne Kopie in `Data`. Auf Gemma 4 26B-A4B mit 1–8 Bildern ist der Spitzen-Speicherbedarf des Prozesses 70–95 MB niedriger, TTFT unverändert (#345) |
| `--experimental-smallm-kernel` | **Experimentell**, standardmäßig aus (entspricht `BASALT_SMALLM_KERNEL=1`): 4–8-zeilige Forward-Passes von 4-Bit-affinen Linear-Layern (Speculative-Lookup- und MTP-Verify-Fenster, Batched-Decode) laufen über den Simdgroup-Matrix-Kernel von Basalt, der jedes Gewicht einmal für alle Zeilen dekodiert. M4 Pro, Qwen3.8-27B-Shapes: 1.5–1.7× der Ein-Token-Zeit bei beliebigen 4–8 Zeilen, wo der Standard-Kernel 1.7–1.9× bei 4 und 3.3–3.7× bei 8 benötigt; Ausgaben unterscheiden sich durch bf16-Rundung vom Standard, sodass Greedy-Identität auf echten Modellen noch ungeprüft ist (#208) |
| `--experimental-adaptive-thinking-budget` | **Experimentell**, standardmäßig aus: eine Anfrage, die weder `thinking_budget` noch `reasoning_effort` setzt, erhält ein Thinking-Budget anhand einer Schwierigkeitsschätzung der letzten Benutzernachricht (Schlüsselwörter wie „prove“ oder „algorithm“, Länge, Tools): leicht 512 Tokens, mittel 2048, schwer unbegrenzt. Nur für Reasoning-Modelle mit Budget-Übergang (Qwen3.x, LFM2.5); ungemessen bis der #41-Lauf vorliegt |
| `--require-verified` | berechnet vor dem Laden den Hash des Snapshots gegen seine Sidecars oder die Hub-Digests neu und verweigert den Start bei jeder nicht verifizierten Datei (#367) |
| `--port`, `--host` | Standard 127.0.0.1:8080; jeder andere Host erfordert einen API-Key (`BASALT_API_KEY` oder `--auto-generate-key`) |
| `virtual_keys` (nur Konfiguration) | zusätzliche API-Keys mit eigenem Cloud-Budget: `"virtual_keys": [{"key": "vk-…", "id": "team-a", "max_budget": 2.0}]` in `~/.gem/config.json`; ein Key ist mindestens 16 Zeichen lang, IDs und Keys sind eindeutig; Ausgaben pro Key überdauern Neustarts |
| `--expert-streaming`, `--no-expert-streaming` | streamt geroutete Mixture-of-Experts-Gewichte aus SSD-Safetensors-Shards (`F_NOCACHE`-gebatchte asynchrone Lesevorgänge in feste LRU-Slots, `--expert-cache-gb` standardmäßig 25% der Expertengewichte). Automatisch aktiviert, wenn ein lokaler gestapelter `SwitchLinear`-Checkpoint in die `Streaming`-Passformstufe fällt (`weights > workingSetBudget`, während residente Gewichte + Experten-Cache passen); deaktivierbar mit `--no-expert-streaming` oder `BASALT_NO_EXPERT_STREAMING=1` (`--experimental-expert-streaming` bleibt als Alias erhalten, #225, #226) |
| `--speech-analyzer` | bedient `/v1/audio/transcriptions`, `basalt_transcribe` und Audio in `/v1/pipeline` über macOS `SpeechAnalyzer` auf der Neural Engine, sofern kein dedizierter Audio-Encoder geladen ist (Alias `--experimental-speech-analyzer`, #222, #226, #230) |
| `--ane-vision-tower DIR` | führt den Vision-Encoder von PaddleOCR-VL auf der Neural Engine aus einem Core-AI-Bundle (`metadata.json` + `tower.aimodel`) aus und persistiert spezialisierte Artefakt-Bookmarks und Metadaten unter `~/.basalt/cache/coreai-vision/`, geschlüsselt nach Bundle-SHA-256 und macOS-Build (Alias `--experimental-ane-vision-tower`, #224, #226, #400) |
| `--max-concurrent N`, `--max-queue N` | gleichzeitig dekodierende Generierungen (Standard 1; jede hält ihren eigenen KV-Cache) und Anfragen in der Warteschlange (Standard 8), nach Priorität — `basalt chat` zuerst, dann Service-Anfragen (Titel, Zusammenfassungen) und Harness-Probes, dann API-Traffic, dann Benchmarks — und innerhalb einer Stufe nach Eingangsreihenfolge; findet eine Anfrage höherer Priorität die Warteschlange voll vor, verdrängt sie den Wartenden mit der niedrigsten Priorität; darüber hinaus antwortet der Server mit 503 und `Retry-After` (ein Stream, der seine Header bereits gesendet hat, erhält stattdessen ein Error-Event). Ein Modellwechsel wartet auf laufende Generierungen und neue Anfragen reihen sich dahinter ein; zwei Ladevorgänge desselben Modells teilen sich einen, das Laden eines anderen Modells liefert währenddessen 503. Bei SIGTERM/SIGINT erhalten Generierungen 5 s zum Beenden und werden danach abgebrochen, damit der Prozess endet |
| `--batch-slots N` | mit `--max-concurrent` 2 oder mehr dekodieren bis zu N Generierungen gemeinsam in einem gebatchten Forward-Pass (Standard 1, aus). Unterstützt Full-Attention-, Recurrent-State- und Sliding-Window-Layer (Qwen3 dense/MoE, Qwen3.5/3.8- und Nemotron-H-Hybriden, LFM2, Gemma 4: Zeilen teilen sich einen Ring des Fensters, links-gepaddet und maskiert wie die Full-Attention-Zeilen, #255) sowohl auf fp16-KV (`BatchKVCache`) als auch bei einheitlichem affinem `--kv-bits` (`4`, `8` oder gleiche Stufe bei `auto` über `BatchQuantizedKVCache`, #243), plus zeilenspezifische `response_format`- / erzwungene Tool-Grammatikmasken; Anfragen mit `--kv-zones`, `k8v4`, `polar4`, `turbo*`, Grammar-Jump-Forward, Prompt-Lookup, MTP, CacheBlend oder Medienanhängen dekodieren wie bisher solo (siehe Matrix unten). Prefill und Prompt-Cache bleiben unverändert; jede Zeile behält ihren eigenen Sampler, eigene Stop-Tokens und `max_tokens`. Gebatchte Greedy-Ausgaben entsprechen in der Qualität dem Solo-Modus, aber nicht Bit für Bit: MLX wählt für eine Zeile andere Kernels als für mehrere (quantisiertes Matmul), und eine für einen längeren Nachbarn links-gepaddete Zeile liest ihre Keys in einer anderen Reihenfolge, sodass die Zusammensetzung eines Schritts knappe Entscheidungen kippen kann (#319). Zeilen, die einander kein Padding hinzufügen, lassen die Logits der anderen unverändert |
| `--session-log full\|meta\|off` | lokales JSONL-Sitzungsprotokoll unter `~/.basalt/sessions/<date>/<session>.jsonl` (`0700`/`0600`): eine `request`-Zeile vor dem Engine-Aufruf und eine `response`-Zeile danach (Status, Tokens, Timing, Speicher, Abbruchgrund) für jeden Endpunkt, plus `error`-Zeilen für abgelehnte Anfragen (nur Größe, niemals Body oder Header) und `model_switch`. `full` (Standard) speichert auch Konversation und Antwort, `meta` nur Größen und SHA-256-Hashes; `--session-log-dir`, `--session-log-retention-days` (14), `--session-log-max-total-mb` (1024); die Sitzung wird über `X-Basalt-Session` (oder `x-session-id`) benannt; ohne Angabe schließt sich eine Anfrage, die eine frühere Konversation fortführt, deren Sitzung an, alles andere startet eine neue. **Wiederverwendung des Prompt-Caches.** Der Server hält den KV-Cache des Modells für aktuelle Prompts in einem Präfixbaum: Prompts, die mit denselben Tokens beginnen, teilen sich eine gespeicherte Kopie dieses Anfangs, und eine Anfrage führt das Prefill nur für das aus, was nach dem längsten gespeicherten Präfix folgt. Dadurch kostet der nächste Zug einer Konversation nur seine neuen Tokens (ein an ein langes Agenten-Transkript angehängtes Tool-Ergebnis, nicht erneut der gesamte Verlauf), und eine zweite Konversation, die mit demselben System-Prompt und denselben Tools startet — ein Claude-Code-Subagent, ein weiterer Codex-Thread — setzt am gemeinsamen Teil an, statt ihn erneut zu prefillen. Der Abgleich erfolgt über Tokens, sodass keine Konversations-ID benötigt wird (`prompt_cache_key`, `metadata.user_id` und `x-session-id` werden ignoriert); ein Client, der seine Prompts getrennt halten möchte, sendet `X-Basalt-Cache-Key: <name>` (1-256 Bytes, auf jedem Generierungs-Endpunkt) und erhält einen eigenen Baum, der sich das Byte-Budget teilt, aber kein Präfix mit dem gemeinsamen Baum oder anderen Keys; Titel- und andere Service-Anfragen berühren den Cache nie. Unter dem Budget `--prompt-cache-mb` wird der am längsten nicht genutzte Zweig von seinem Ende her gekürzt (der Snapshot-Zweig eines Hybrid-Modells, siehe unten, wird vollständig entfernt, da sein rekurrenter Zustand nur an seinem Ende gültig ist), sodass eine ruhende Konversation ihren System-Prompt und ihre Tools am längsten behält und der Knoten, bis zu dem eine laufende Anfrage wiederverwendet, nie verdrängt wird (bei einem Hybrid-Modell ist das sein Snapshot-Knoten; die Anfrage hat ihre eigene Kopie der Daten, sodass das Verdrängen des restlichen Zweigs sie nicht beeinflussen kann); der Baum hält außerdem höchstens 4096 Zweige und verwirft darüber hinaus den am längsten nicht genutzten freien Zweig. Usage weist aus, was tatsächlich wiederverwendet wurde: `prompt_tokens_details.cached_tokens` (Chat Completions), `input_tokens_details.cached_tokens` (Responses), `cache_read_input_tokens` (Anthropic, wobei `input_tokens` nur den neu geprefillten Rest zählt). Hybride Attention-/SSM-Modelle wie Qwen3.5/3.6 und Ornith-1.5 sowie Gemma 4 mit seinen Sliding-Window-Layern verwenden ebenfalls den vorherigen Turn einer Konversation wieder: Ihr rekurrenter oder rotierender Zustand lässt sich nicht zurückspulen, daher legt der Server beim Prefill eines Prompts einen Snapshot davon am Ende des Anfragetexts vor den schließenden Tokens des Chat-Templates an, und der nächste Turn, der diesen Text erweitert, stellt den Snapshot wieder her und prefillt nur das Folgende (Ornith-1.5-9B, 12.6k-Token-Agenten-Prompt: der zweite Turn dauert etwa 1 s statt etwa 36 s). Ein wiederverwendeter Turn kann nach seinen ersten Tokens von einem uncached Lauf abweichen: Das Prefill wird anders in Chunks unterteilt, was bf16-Ergebnisse leicht verschiebt (gemessen auf Ornith: Der wiederhergestellte Zustand ist bitweise identisch mit einem von Grund auf neu gerechneten Prefill, der an denselben Stellen geteilt wird, und weicht von einem Ein-Phasen-Prefill in den Logits der letzten Position um höchstens 1.56 bei identischen Top 5 ab; auf Gemma 4 12B ist der wiederhergestellte Cache ebenfalls bitweise identisch, und über eine zwölfstufige Sitzung von ~4k Tokens weicht er von einem Ein-Phasen-Prefill um 0.60–2.33 bei gleichem Greedy-Token ab — ungefähr so viel, wie ein Ein-Phasen-Prefill in 256-Token- statt 512-Token-Chunks von sich selbst abweicht, 2.53, sodass bei Temperatur 0 ein knappes Token noch kippen kann). Sie verwenden ausschließlich einen solchen Snapshot wieder, sodass eine zweite Konversation mit demselben System-Prompt vollständig geprefillt wird. `--kv-bits` prefillt immer den gesamten Prompt.

**CacheBlend (Opt-in, approximativ).** Der Präfixbaum hilft nur, wenn ein Prompt gleich beginnt; ein Agent, der dieselben Dateien in anderer Reihenfolge einfügt, prefillt alle erneut. `--cache-blend` speichert zusätzlich das KV jedes Prompt-Chunks — ein Chunk endet nach jeder Leerzeile, unabhängig davon, ob der Tokenizer sie als ein Token oder als zwei Zeilenumbruch-Tokens schreibt, sodass durch Leerzeilen getrennte Dateien und Nachrichten eigene Chunks behalten; Chunks unter 16 Tokens werden immer neu berechnet — und verwendet einen Chunk überall dort wieder, wo er in einem späteren Prompt landet (Keys werden vor RoPE gespeichert und an die neue Position rotiert). Die zwischengespeicherten Chunks wurden neben anderem Text berechnet, ihr KV ist daher veraltet: Nach CacheBlend (arXiv:2405.16444) wird der erste Layer für jedes Token neu berechnet, und nur `--cache-blend-ratio` der wiederverwendeten Tokens (Standard 0.3) sowie jedes nicht im Store vorhandene Token werden auf den späteren Layern neu berechnet. Das Budget geht zuerst an die ersten 32 Tokens jedes wiederverwendeten Chunks, deren Kontext sich beim Verschieben des Chunks am stärksten verändert hat (wie in EPIC, arXiv:2410.15332), geordnet nach der Abweichung ihres KV auf dem zweiten Layer, und erst danach an die am stärksten abweichenden Tokens des Rests. Der geblendete Forward-Pass kostet etwa das 1.2× des modelleigenen Prefills pro neu berechnetem Token, sodass ein Prompt nur dann geblendet wird, wenn (1 − ratio) × der Anteil wiederverwendeter Tokens mindestens 0.2 beträgt und der gesamte Cache innerhalb von 16 384 Tokens bleibt; andernfalls — ein frischer Prompt, geringe Wiederverwendung, `--cache-blend-ratio 1`, ein langer Kontext — nutzt es das modelleigene Chunked-Prefill, und seine Chunks werden aus diesem Cache gespeichert (Keys werden aus Post-RoPE zurückrotiert, exakt bis auf die dtype-Rundung des Caches, ~2⁻⁸ relativ in bf16). Das Ergebnis ist approximativ. Gemessen auf Qwen3-4B-4bit (M4 Pro) mit sechs eingefrorenen Dateien à 550–900 Tokens (`benchmarks/cacheblend`) in vier neuen Reihenfolgen, jeweils mit einer neuen Frage (4 854 von ~5 066 Tokens aus Chunks), bewertet anhand der Greedy-Antwort des vollständigen Prefills (50 Tokens) unter Teacher Forcing — mittlere Log-Wahrscheinlichkeit der Referenz-Tokens und Top-1-Übereinstimmung pro Position auf dieser Stichprobe von 200 Positionen (0.01 entspricht zwei Positionen):

| Cache | Log-Prob | Top-1 | Perplexität |
|---|---|---|---|
| vollständiges Prefill | −0.094 | 0.995 | 1.099 |
| ratio 0 | −0.180 | 0.925 | 1.198 |
| ratio 0.15 (Wert aus dem Paper) | −0.166 | 0.945 | 1.181 |
| **ratio 0.3 (Standard)** | −0.123 | 0.960 | 1.131 |
| ratio 0.5 | −0.125 | 0.970 | 1.134 |
| ratio 1 (natives Prefill) | −0.094 | 0.995 | 1.099 |

Dass Chunk-Anfänge zuerst neu berechnet werden, macht 0.3 zum Standard: Mit Layer-1-Abweichung allein ließ ratio 0.3 eine Perplexitätslücke von 0.085 und selbst 0.5 ließ 0.038; mit Chunk-Anfängen zuerst lässt 0.3 nur 0.032 (0.50: 0.035). Bei vier anderen Reihenfolgen und Fragen zu denselben Dateien ist die Lücke größer (0.096 bei 0.3, gegenüber 0.169 ohne Chunk-Anfänge und 0.120 beim alten Standard 0.5), sodass die Schranke von 0.05 für die Benchmark-Stichprobe gilt, nicht für jeden Prompt. `--cache-blend-ratio 0` tauscht Qualität gegen das kürzeste Prefill. Nur Dense-Modelle der Llama- und Qwen3-Familie; andere Modelle behalten den exakten Präfix-Pfad. Bei aktiviertem Flag wird das Budget des Prompt-Caches hälftig zwischen dem Baum und dem Chunk-Store aufgeteilt. `cached_tokens` zählt weiterhin nur die exakten Präfixbaum-Tokens; geblendete Tokens werden in `prompt_tokens` gezählt und protokolliert (`[CacheBlend] Blended N prompt tokens: R from cached chunks, X of them recomputed`), und der Baum speichert nur den exakten Anfang eines geblendeten Prompts. Ein geblendeter Durchlauf hält kurzzeitig den zusammengesetzten Cache und die unrotierten Keys und Values der Chunks gleichzeitig im Speicher (etwa das Doppelte des Prompt-KV, z. B. ~5 GB für 16k Tokens von Qwen3-4B), was in den Speicherschätzungen nicht enthalten ist. Bei kleinen Verhältnissen dominieren die Fixkosten der Layer 0–1 und des Abweichungs-Passes, sodass 0.15 und 0.3 langsamer sind, als das lineare Kostenmodell vermuten lässt. Standardmäßig deaktiviert, da es Ausgaben verändert; `--prompt-cache-mb 0` schaltet es ebenfalls ab.

Datenschutz: Alle Clients teilen sich einen Präfixbaum, und `cached_tokens` verrät, wie viele führende Tokens ein Prompt mit früheren Prompts gemeinsam hat, sodass ein Aufrufer sondieren kann, was ein anderer Client gesendet hat. Auf einem Server, der von Personen gemeinsam genutzt wird, die die Prompts der anderen nicht sehen dürfen, starten Sie mit `--prompt-cache-mb 0`; mit `--cache-blend` zeigt außerdem die Time-to-First-Token, welche Chunks ein anderer Client gesendet hat.
