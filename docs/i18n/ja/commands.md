# コマンド

> Languages: [English](../../commands.md) · [Русский](../ru/commands.md) · [中文](../zh/commands.md) · [Español](../es/commands.md) · [Français](../fr/commands.md) · **日本語** · [Deutsch](../de/commands.md) · [한국어](../ko/commands.md) · [Bahasa Indonesia](../id/commands.md)

サブコマンドを指定せずに `basalt` を実行すると、`chat` が起動します。

| コマンド | 説明 |
|---|---|
| `basalt onboard` | 初回セットアップウィザード：お使いのマシンに適したモデルを選択してダウンロードします |
| `basalt fit` | ハードウェア情報を読み取り、それに応じてモデルカタログをランク付けします |
| `basalt chat --model <id>` | 対話型のターミナルチャットを起動します |
| `basalt serve --model <id> --rest` | ポート :8080 で REST サーバーを起動します（OpenAI および Anthropic 互換） |
| `basalt serve --model <id> --mcp` | Claude Desktop / Cursor 向けの MCP stdio サーバーを起動します |
| `basalt serve --model <id> --stats` | 5 秒ごと（`--stats-interval`）にテレメトリを stderr へ出力します。同じ数値は `GET /api/v1/stats` および MCP の `status` でも取得できます |
| `basalt serve --model <id> --canary-minutes 30` | 30 分ごとにアイドル状態のとき、バックグラウンド優先度で既知回答のリクエストを 1 件送信します。合否、縮退出力（degenerate-output）の回数、モデルごとの tok/s およびドラフト受理率のドリフトは `GET /api/v1/stats` の `health` 配下に記録されます（#325） |
| `basalt models list --author <org>` | HuggingFace の特定の作成者によるモデル一覧を表示します |
| `basalt models download <repo-id>` | 共有の HF キャッシュへモデルをダウンロードします |
| `basalt models info <repo-id>` | サイズ、量子化形式、コンテキストウィンドウを表示します |
| `basalt models cache` | ディスク上に保存されているモデルと使用容量を表示します |
| `basalt models check <repo-id>` | メモリに収まるかを確認します（収まらない場合はゼロ以外の終了コードで終了） |
| `basalt models check --deep <repo-id>` | さらにダウンロード前に safetensors ヘッダー（数百 KB）のみを取得し、それらに合わせてシェイプのみでモデルを構築してチャットテンプレートをレンダリングします。不足・余剰・シェイプ不一致のテンソル、未対応の `model_type`、テンプレートエラーを一覧表示し、ゼロ以外の終了コードで終了します |
| `basalt models inspect <repo-id>` | キャッシュ済みモデルが完全であるかを検証し、実際のビット幅を測定します |
| `basalt models inspect --verify <repo-id>` | さらにキャッシュ内の各ファイルをサイドカーまたは Hub のダイジェストと照合して再ハッシュし、ファイルごとに `true`、`false`、`unknown` を返します（読み取り専用、#367） |
| `basalt models distill <model> --prompts FILE --teacher-url URL --teacher-model NAME` | OpenAI または Anthropic 形式 API（`--provider`）背後の教師モデルをローカルモデル向けの LoRA に蒸留します。API キーは `BASALT_TEACHER_API_KEY`、URL は `BASALT_TEACHER_URL` から読み込みます。`--budget-usd` で上限金額前に停止し、`--filter verify` でプロンプトの `answer` に一致する回答のみを残します。`--on-policy` では生徒モデルがサンプリングし、同じトークナイザーを持つ basalt 教師モデルが `/v1/score` でそのトークンをスコアリングします（トークン単位の逆 KL）。オフライン実行では `--checkpoint-every` ステップごとにチェックポイントを保存し、`--resume` で再開できます（#393） |
| `basalt models train-jepa <model> --dataset FILE` | マルチビューデータセット（1 シーンにつき JSONL 1 行、最低 2 ビュー）上で JEPA LoRA アダプターとプロジェクターを学習し、学習前後の損失と埋め込みランクを出力します |
| `basalt models convert <source> --out DIR` | ユニバーサル any-to-any コンバーター（#546）：`--to macaq:affine|mxfp4|moe`（ブロック Walsh–Hadamard + Hessian 反転精密化、ルーター重み付き 2.8 bpw MoE #599）、`--to flatquant` / `--to lirquant`（#594）、`--to sinq` / `a-sinq` / `eaquant`（#561）、`--to e8p`（`QuIP#` 2 ビット格子 + `TurboBoA` Babai–LLL、#589）、`--experimental-qtip 2.0\|2.5\|3.0`（#494）、`nf4`、`SVD-LLM V2` / `OBR`（#592）、`.gguf` ネイティブ i-quant および `MACaQ-R` 間で再量子化でき、さらに `--pv-tune`（`--pv-preset fast|full`、#545）、ドメイン認識 QAT STE 精密化、量子化後の品質・公平性・リーク監査（`#623`）を備えています。REST `/v1/models/convert*` および macOS の `ConvertModelSheet` からも利用可能です |
| `basalt serve --video-model <id> --rest` | 因果的 3D-VAE、STA Metal カーネル、`AVAssetWriter` による `.mp4` マルチプレクスを備え、`/v1/videos/*` 上でフェーズ分割 24 GB UMA Video Studio（`LTX-2.5 AV-DiT`、`Kandinsky 6.0`、`LingBot-Video MoE`、`Wan 2.2`）を提供します（#608–#611, #614） |
| `basalt review --diff FILE\|- --model <id>` | ローカルモデルで差分をレビューします。`--gitlab` / `--gitea URL --repo R --number N` を指定するとマージリクエストを取得し、`--post` でレビュー結果を投稿します（`GITLAB_TOKEN` / `GITEA_TOKEN`）（#35） |
| `basalt compose` | マルチモデル YAML システム（`models`、`pipeline`、`pipelines`、`experimental`、`mcp`、`variables`、`profiles`）の起動、計画、差分確認、プル、停止を行います。`/v1/compose/apply` を通じてモデル、パイプライン、バジェット、およびライブの `experimental` 設定（`speech_analyzer`、`image_fallback`、`telemetry_confidence_every`、`adaptive_thinking_budget`）をホットリロードします（#412, #423, #485） |
| `basalt cloud configure` | ローカルに収まらない処理のための OpenRouter フォールバックを設定します |
| `basalt cloud cost` | これまでのクラウドフォールバックの累計利用額を表示します |

`basalt chat` 内でのコマンド：

| 入力 | 動作 |
|---|---|
| `/clear` | 会話履歴と画面を消去します |
| `/color`、`/theme` | ターミナルのカラーテーマを切り替えます |
| `exit`、`quit` | チャットを終了します（スラッシュなし） |

`serve` で知っておくと役立つ主なフラグ：

| フラグ | 用途と詳細 |
|---|---|
| `--reasoning-effort none` | 推論モデルが `<think>` 内でトークン予算をすべて使い切らないようにします |
| `--reasoning-effort xhigh\|medium\|low` | Qwen ファミリーの思考トークン予算を指定します |
| `--quant 4bit` | 複数の量子化サブフォルダを提供するリポジトリから特定の量子化を選択します |
| `--kv-bits 4\|8\|auto` | KV キャッシュを量子化し、メモリに余裕のないマシンで生成用の空き容量を確保します。プロンプトキャッシュの再利用は無効になります。MLX はプロンプトを fp16 でプリフィルしてから量子化するため、プロンプト自体を fp16 より長くすることはできません（変換時に一時的に両方のコピーを保持するため、むしろ短くなります）。`auto` は、リクエストのプロンプトと `max_tokens` の合計が収まる間はプロンプトキャッシュ再利用付きの fp16 を維持し、収まらない場合はそのリクエストのみ 8 ビット、それも無理なら 4 ビットで実行します |
| `--kv-bits turbo3\|turbo4\|turbo8v4` | **実験的機能**（#471）：フルアテンション層に対する本フォーク独自の TurboQuant キャッシュ（回転、Lloyd–Max コードブック、ベクトルごとのノルム；対象となる最初と最後の各 2 層は 8 ビットアフィンを維持）。`--kv-zones` とは併用できません。8k コンテキストの M4 Pro 上でのアフィン 4 ビットとの比較実測値：デコード速度は 8–13% 低下（Qwen3.8-27B は 13.8 vs 15.0 tok/s、LFM2.5-24B は 82 vs 94）、384 トークンのデコードパープレキシティは Qwen3.8 で 4 ビットの +1.5% に対し +0.3% / +1.3%、LFM2.5 で +5.0% に対し +10.1% / +3.6%、16k 時点の KV サイズは縮小せず（Qwen3.8 は 461 MB に対し 460 / 511 MB、LFM2.5 は 97 MB に対し 118 / 131 MB、Gemma 4 26B-A4B は 306 MB に対し 423 MB）。圧縮はデコード時に適用され、マルチトークンチャンクでは生のキーが読み取られます |
| `--kv-bits polar4` | **実験的機能**（#351）、`--kv-zones` 併用時：ゾーン分けされた中間部では、各キーの RoPE ペアを 1 バイト（5 ビット位相、初回マイグレーションバッチからヘッドおよびペアごとにスケーリングした Rayleigh 分位点に基づく 3 ビット絶対値）として格納し、残りの次元はアフィン 4 ビットで格納します。値はアフィン 4 ビットのままです。RoPE が次元 i と i + d/2 をペアにする Qwen3、Qwen3.5、LFM2 のみが対象で、他のモデルではアフィンキーを維持し、その旨をログに出力します。M4 Pro で 8k コンテキスト後に 256 トークンをデコードした場合のゾーン分け q4 および k8v4 との比較実測値：パープレキシティは Qwen3.8-27B が 8.61 vs 8.56 / 8.50、LFM2.5-24B が 61.2 vs 76.5 / 70.9（ノイズの多い 256 トークンサンプル）、ゾーン分け KV は 196 vs 197 / 255 MB および 59 vs 62 / 80 MB、デコード速度は 12.4 vs 14.0 / 14.6 tok/s および 11.3 vs 19.5 / 18.2（専用 polar カーネルがないため中間部を毎ステップ fp16 にデコード）。16k パスキーテストでは両モデルとも深度 0.2 と 0.8 で発見に成功しました。オフライン実験では、同ビット幅で polar がアフィンを上回ることは確認されていません |
| `--kv-bits k8v4` | `--kv-zones` 併用時：量子化される中間部でキーを 8 ビット、値を 4 ビットで格納します（グループスケールを含め K+V ペアあたり 13 ビットで fp16 の 0.41×、8 ビットの 0.53× と 4 ビットの 0.28× の中間）。`--kv-zones` 付きの `auto` は 8 ビットと 4 ビットの間にこの設定を試行します。ゾーンが適用されないモデル（Gemma 4）では均一な 8 ビットとして動作します。**実験的機能：** `k8v4h` は 4 ビット量子化の前に値へ Walsh–Hadamard 変換を適用し（読み取り時に逆変換）、外れ値チャネルを分散させます。これは明示指定時のみ有効で、`auto` が選ぶことはありません。8k コンテキスト後に 8k トークンを評価した `k8v4` とのパープレキシティ比較実測値：Qwen3-4B が 6.568 vs 6.562、Ornith-1.5-9B が 4.937 vs 4.920、LFM2.5-8B が 8.723 vs 8.750（各 1 回実行、誤差範囲内）。16k プロンプト後のピークメモリは Ornith で約 85 MB、Qwen3-4B で 30–150 MB 増加しました（回転対象となる値の fp32 コピー分）。変換が自身の逆変換となるヘッド次元 2^k および 12·2^k のみを回転し、その他のヘッド次元は非回転のまま維持され、`serve` ロード時にログ出力されます。より長いコンテキスト（32k+）や V に外れ値チャネルを持つモデルで有効な可能性がありますが、未検証です |
| `--kv-zones` | `--kv-bits` 併用時：各フルアテンション層の先頭 64 トークンと末尾 1024 トークンを fp16 に保ち、プロンプトのプリフィル時にその間のトークンのみを量子化します。変換元となる fp16 プリフィル全体を持たないため、プロンプトに量子化後の全容量を使え、ピークメモリが低下します。Qwen3-4B で 8k コンテキスト後に 8k トークンを評価した場合、4 ビットのパープレキシティは fp16 の 6.56 および均一 4 ビットの 8.66 に対し 6.58 となります |
| `--kv-evict F` | **実験的機能**、`--kv-zones` 併用時：トークンが直近ウィンドウを離れる際、各フルアテンション層の量子化済み中間部から割合 `F`（0–0.9）を破棄します。KV ヘッドごとにキーの L2 ノルムが最大のものを優先して保持（または対象外とし）破棄します（arXiv:2406.11430）。アテンション重みを必要としないため、アテンション計算は融合カーネル上のまま維持されます。シンクと直近ウィンドウは決して破棄されず、`serve` および `models check` が報告する空き容量は保持されるトークンのみを計算に入れます。k8v4 を用いた 16k プロンプト後の Qwen3-4B の KV 容量は 1.11 GB から、0.25 指定時で 0.89 GB、0.5 指定時で 0.66 GB に低下します。品質面では代償があり、パープレキシティ（8k 後に 8k 評価）は Qwen3-4B で 6.56 に対し 6.71 / 7.04、LFM2.5-8B で 8.75 に対し 9.06 / 9.52、Ornith-1.5-9B では変化なしでした。0.25 指定時の 16k パスキーは Qwen3-4B と Ornith で 5 つの深度のうち 1 つで失われ、グリーディ出力は最初の数トークン以内で fp16 と乖離します。Gemma 4、および直近ウィンドウを超える長さを 1 パスでプリフィルするモデル（ロード時に判定）は全トークンを保持し、それに応じたサイズ計算を行います |
| `--kv-head-split R` | **実験的機能**、均一 `--kv-bits` とは併用不可：長いプロンプトの中盤から事実を読み取る KV ヘッドの割合 `R`（0.05–1）にのみ全コンテキストを保持し（DuoAttention に基づき、合成パスキーセットでモデルごとに 1 度スコアリングして `~/.basalt/head-scores` にキャッシュ）、残りのヘッドは 128 個のシンクトークンと 256 個の直近トークンのみを保持します。Qwen3-4B（32k、`R` 0.25）での実測値：KV は 4.76 → 1.26 GB、デコードは 27.2 → 36.2 tok/s、パスキーは 16k および 32k で 10/10 でした。Qwen3.5 ファミリーおよび LFM2 / Nemotron-H ハイブリッド、ならびにキャッシュを経由しないアテンションを持つモデル（Gemma 4）では警告を出して拒否されます。ハイブリッドモデルでは、アブレーションにより選択した 25% で 16k パスキーを喪失し（Qwen3.8-27B は 0/3 深度、LFM2.5-24B は 2/3）、パープレキシティがそれぞれ 24% および 42% 悪化しました（出力忠実度によるヘッド選択は #282 で追跡中）。`--kv-zones --kv-bits k8v4` 併用時（実験的機能、両方指定した場合のみ有効）は、保持対象ヘッドが長いコンテキストをゾーン分けして格納します（先頭 64 と末尾 1024 トークンは厳密なまま、中間部は 8 ビットキー・4 ビット値、その他のヘッドは上記のまま）。`--kv-zones` と同様、プロンプトキャッシュ名前空間を持たないリクエストに適用されます |
| `--prompt-cache-mb N` | プロンプトキャッシュのプレフィックスツリー用に確保するメモリ容量（デフォルト：ウェイト読み込み後に Metal 推奨 GPU ワーキングセットに残る容量の半分、ロード時にログ出力；`0` で無効）。詳細は後述 |
| `--prompt-cache-disk-mb N` | 正常終了時、モデル切り替え前、および `basalt chat` 終了時にプロンプトキャッシュを `~/.basalt/prompt-cache/`（`--prompt-cache-dir`）へ永続化し、再開したセッションや再起動後のサーバーがプリフィルせずディスクからプレフィックスを復元できるようにします（デフォルト `0`、無効）。最も参照頻度の高いブランチから順に、最大 `N` MB かつ想定 1 GB/s でシャットダウン期限内に書き込みが完了する分のみを書き出します。同じ会話のより長いパスはそれがカバーする短いファイルを置き換え、空き容量確保のため最も長く使われていない（LRU）ファイルから削除されます。`--prompt-cache-disk-days`（7）日間未使用のファイルは起動時に削除され、`basalt sessions prune` でも同じ処理をオフラインで実行できます。ディレクトリは新規、空、または既存のプロンプトキャッシュディレクトリである必要があります（他のファイルを含むディレクトリは拒否されます）。ファイルは同一モデル（ウェイトブロブ、または HF キャッシュ外の場合はサンプリングされたウェイト内容、設定、トークナイザー、チャットテンプレート）、同一 basalt バージョン、同一キャッシュ形式でのみ使用され、それ以外の場合や切り詰められたファイル、異なるレイヤー構成では通常のプリフィルにフォールバックします。`--session-log full`（ファイルに会話を KV テンソルとして保持するため）とメモリ内プロンプトキャッシュが必要です。`--kv-bits`、`--kv-zones`、およびマルチモーダルプロンプトは決して永続化されません |
| `--cache-blend` | キャッシュされたプロンプトチャンクを任意の順序で近似的に再利用します（CacheBlend）。`--cache-blend-ratio R` で再計算する割合を指定します（デフォルト 0.3）。詳細は後述 |
| `--min-p`、`--top-k`、`--seed` | サンプリング設定。`--seed` を指定すると非グリーディ実行に再現性を持たせられます。リクエスト側の `min_p` は `--min-p` を上書きします |
| `--max-tokens` | デフォルトの生成上限トークン数（2048–128000） |
| `--dry-run` | メモリ収容可能性のチェックのみを行い、モデルをロードせずに終了します |
| `--config basalt.yaml` | YAML ファイルからサーブオプションを読み込みます。`defaults.{model,serve,mcp}` 配下のキーが対応するフラグになり、コマンドライン上のフラグが優先されます。未知のキーは行・列番号付きで報告されます（#344） |
| `--mcp-enable <tool\|group>`、`--mcp-disable <tool\|group>` | `--mcp` 併用時に、`--research-tools` 全体を公開することなく個別の MCP ツールまたはグループ（`serving`、`gemma`、`media`、`harness`、`xray`、`surgery`、`research`、`all`）を選択的に有効・無効化します。`--mcp-disable` は常に `--mcp-enable` や `--research-tools` に優先し、未知の名前は起動時に即座にエラーとなります。`basalt.yaml` の `defaults.mcp.enable` / `defaults.mcp.disable` でも設定可能です（#484） |
| `--adapter name=dir` | 常駐しているベースモデル上に mlx-lm LoRA アダプターをロードします（複数回指定可）。リクエスト側では `X-Basalt-Adapter: name` で選択します。同一アダプターへのリクエストは一緒に実行され、切り替え時は実行中の生成の完了を待ち、各アダプターは独自のプロンプトキャッシュ名前空間を持ちます。ベースモデルのどの層にも適合しないテンソルを持つアダプターは起動時に拒否されます（#179） |
| `--experimental-zero-copy-body` | **実験的機能**：各 REST リクエストボディをコピーせずに `Data` でラップします。1–8 枚の画像を伴う Gemma 4 26B-A4B ではプロセスフットプリントのピークが 70–95 MB 低下しますが、TTFT は改善しません（#345） |
| `--experimental-smallm-kernel` | **実験的機能**、デフォルトオフ（`BASALT_SMALLM_KERNEL=1` と同等）：4 ビットアフィン線形層の 4–8 行のフォワードパス（投機的ルックアップや MTP 検証ウィンドウ、バッチデコード）を、全行に対して各ウェイトを 1 度だけデコードする basalt の simdgroup-matrix カーネル経由で実行します。M4 Pro、Qwen3.8-27B のシェイプでの実測値：標準実装が 4 行で 1.7–1.9×、8 行で 3.3–3.7× かかるのに対し、4–8 行のいずれでも 1 トークン時間の 1.5–1.7× となります。出力は bf16 の丸め誤差により標準実装と異なるため、実モデルでのグリーディ一致性はまだ検証されていません（#208） |

**プロンプトキャッシュの再利用。** サーバーは直近のプロンプトに対するモデルの KV キャッシュをプレフィックスツリーに保持します。先頭が同じトークンで始まるプロンプトはその開始部分の保存済みコピーを 1 つ共有し、リクエストは保存済みの最長プレフィックスに続く部分のみをプリフィルします。そのため会話の次のターンでは新しいトークンのみがコストとなり（長いエージェント記録に追記されたツール結果に対して履歴全体をやり直さない）、同じシステムプロンプトとツールで始まる 2 つ目の会話（Claude Code のサブエージェントや別の Codex スレッドなど）も再プリフィルせず共有部分から開始できます。照合はトークン単位で行われるため会話 ID は不要です（`prompt_cache_key`、`metadata.user_id`、`x-session-id` は無視されます）。プロンプトを他と分離したいクライアントは `X-Basalt-Cache-Key: <name>`（1-256 バイト、すべての生成エンドポイントで利用可能）を送信すると独自のツリーを取得でき、バイト予算は共有しつつも共有ツリーや他のキーとはプレフィックスを共有しません。タイトル生成などのサービスリクエストは一切キャッシュに触れません。`--prompt-cache-mb` 予算の下では、最も長く使われていない（LRU）ブランチが末尾から切り詰められるため（後述するハイブリッドモデルのスナップショットブランチは、リカレント状態がその末尾でのみ有効であるため全体が削除されます）、アイドル状態の会話でもシステムプロンプトとツールが最も長く残り、実行中のリクエストが再利用しているノードまでは決してエビクトされません（ハイブリッドモデルではそのスナップショットノードが該当し、リクエストはデータの独自コピーを持つためブランチの残りがエビクトされても影響を受けません）。ツリーは最大 4096 ブランチも上限とし、それを超えると未使用の最も古いブランチから削除します。実際に再利用された量は usage に報告されます：`prompt_tokens_details.cached_tokens`（Chat Completions）、`input_tokens_details.cached_tokens`（Responses）、`cache_read_input_tokens`（Anthropic；このとき `input_tokens` には残りのプリフィル分のみが計上されます）。Qwen3.5/3.6 や Ornith-1.5 のようなハイブリッド アテンション/SSM モデル、およびスライディングウィンドウ層を持つ Gemma 4 も会話の前ターンを再利用します。これらのリカレント状態やローテーション状態は巻き戻せないため、サーバーはプロンプトのプリフィル中にリクエストテキストの末尾（チャットテンプレートの閉じトークンの直前）で状態のスナップショットを保持し、そのテキストを延長する次のターンでスナップショットを復元して後続部分のみをプリフィルします（Ornith-1.5-9B、12.6k トークンのエージェントプロンプト：2 ターン目は約 36 秒ではなく約 1 秒で完了）。再利用されたターンは最初の数トークンの後に未キャッシュ実行と異なる場合があります。これはプリフィルのチャンク分割が変わり、bf16 の結果がわずかにずれるためです（Ornith での実測値：復元された状態は同じ分割点で最初からプリフィルしたものとビット単位で一致し、1 フェーズのプリフィルとは最終位置ロジットで最大 1.56 差があるものの上位 5 候補は一致。Gemma 4 12B でも復元されたキャッシュはビット単位で一致し、約 4k トークンにわたる 12 ターンのセッションで 1 フェーズプリフィルとの差は 0.60–2.33 に留まり、グリーディトークンは一致しました。これは 1 フェーズプリフィルを 512 トークンチャンクではなく 256 トークンチャンクで実行したときの自己との差 2.53 と同程度であるため、temperature 0 でも僅差のトークンが入れ替わる可能性はあります）。これらはそのようなスナップショットからのみ再利用するため、同じシステムプロンプトを使う 2 つ目の会話はフルプリフィルを行います。`--kv-bits` を指定した場合は常に全プロンプトがプリフィルされます。

**CacheBlend（オプトイン、近似）。** プレフィックスツリーが役立つのはプロンプトの先頭が一致する場合のみであり、同じファイルを別の順序で貼り付けるエージェントはすべてを再プリフィルしてしまいます。`--cache-blend` は各プロンプトチャンクの KV も保持し（チャンクは、トークナイザーが 1 トークンとして書くか 2 つの改行トークンとして書くかにかかわらず空行の直後で終わるため、空行で区切られたファイルやメッセージはそれぞれ独自のチャンクを維持します；16 トークン未満のチャンクは常に再計算されます）、後続プロンプトのどこに現れてもチャンクを再利用します（キーは RoPE 適用前の状態で保存され、新しい位置へ回転されます）。キャッシュされたチャンクは別のテキストの隣で計算されたものであるため、その KV は古くなっています（stale）。CacheBlend（arXiv:2405.16444）に従い、第 1 層はすべてのトークンについて再計算され、再利用されたトークンのうち `--cache-blend-ratio` の割合（デフォルト 0.3）とストアにないすべてのトークンのみが、それ以降の層で再計算されます。予算はまず、チャンクが移動した際にコンテキストが最も大きく変化した各再利用チャンクの先頭 32 トークン（EPIC、arXiv:2410.15332 と同様）に割り当てられ、第 2 層での KV の乖離度が高い順に選ばれ、その後に残りのトークンのうち最も乖離しているトークンへ割り当てられます。ブレンドされたフォワードは再計算トークンあたりモデル自身のプリフィルの約 1.2× のコストがかかるため、(1 − ratio) × 再利用トークン割合が 0.2 以上であり、かつキャッシュ全体が 16 384 トークン以内に収まっている場合にのみプロンプトがブレンドされます。それ以外（新規プロンプト、再利用が少ない、`--cache-blend-ratio 1`、長大コンテキスト）の場合はモデル自身のチャンク化プリフィルが選ばれ、そのキャッシュからチャンクが保存されます（キーは RoPE 適用後から逆回転され、キャッシュの dtype 丸め精度（bf16 で相対約 ~2⁻⁸）まで厳密に一致します）。結果は近似となります。Qwen3-4B-4bit（M4 Pro）上で 550–900 トークンの固定ファイル 6 本（`benchmarks/cacheblend`）を 4 通りの新しい順序に並べ替え、それぞれ新しい質問を添えて（約 5 066 トークンのうち 4 854 トークンがチャンク由来）、フルプリフィルのグリーディ回答（50 トークン）を teacher forcing 下で評価した実測値（この 200 位置のサンプルにおける参照トークンの平均対数確率と位置ごとの top-1 一致率、0.01 は 2 位置に相当）：

| cache | log-prob | top-1 | perplexity |
|---|---|---|---|
| full prefill | −0.094 | 0.995 | 1.099 |
| ratio 0 | −0.180 | 0.925 | 1.198 |
| ratio 0.15 (the paper's value) | −0.166 | 0.945 | 1.181 |
| **ratio 0.3 (default)** | −0.123 | 0.960 | 1.131 |
| ratio 0.5 | −0.125 | 0.970 | 1.134 |

チャンク先頭を優先して再計算することが 0.3 をデフォルトにしている理由です。層 1 の乖離度のみでは ratio 0.3 でパープレキシティ差 0.085 が残り、0.5 でも 0.038 残りましたが、チャンク先頭を優先すると 0.3 で 0.032 に縮まります（0.50 では 0.035）。同じファイルに対する別の 4 通りの順序と質問では差がより大きく（0.3 で 0.096；チャンク先頭優先なしでは 0.169、旧デフォルト 0.5 では 0.120）、0.05 という上限はそのベンチマークサンプル上で成り立つものであり、すべてのプロンプトで成り立つわけではありません。`--cache-blend-ratio 0` は品質を犠牲にして最短のプリフィルを選びます。Llama ファミリーおよび Qwen3 ファミリーの dense モデルのみが対象で、他のモデルでは厳密なプレフィックスパスが使われます。このフラグが有効なとき、プロンプトキャッシュの予算はツリーとチャンクストアで半分ずつに分割されます。`cached_tokens` には引き続き厳密なプレフィックスツリーのトークンのみが計上され、ブレンドされたトークンは `prompt_tokens` に計上されてログ出力され（`[CacheBlend] Blended N prompt tokens: R from cached chunks, X of them recomputed`）、ツリーにはブレンドされたプロンプトの厳密な先頭部分のみが格納されます。ブレンドパスは組み立てられたキャッシュとチャンクの逆回転済みキー・値を同時に一時保持するため（プロンプトの KV の約 2 倍、例：Qwen3-4B の 16k トークンで約 5 GB）、メモリ見積もりにはこの分が含まれません。小さい比率では層 0–1 と乖離度パスの固定コストが支配的になるため、0.15 や 0.3 は線形コストモデルが示唆するよりも遅くなります。出力が変わるためデフォルトではオフになっており、`--prompt-cache-mb 0` を指定した場合も同様にオフになります。

プライバシー：すべてのクライアントは 1 つのプレフィックスツリーを共有し、`cached_tokens` はあるプロンプトが以前のプロンプトと先頭何トークンを共有しているかを明らかにするため、呼び出し元が別のクライアントの送信内容を探ることが可能になります。互いのプロンプトを見られてはならないユーザーが共有するサーバーでは `--prompt-cache-mb 0` を指定して実行してください。`--cache-blend` を有効にすると、TTFT（初回トークンまでの時間）からも別のクライアントがどのチャンクを送信したかが判別可能になります。
