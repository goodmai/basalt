# Comandos

> Languages: [English](../../commands.md) · [Русский](../ru/commands.md) · [中文](../zh/commands.md) · **Español** · [Français](../fr/commands.md) · [日本語](../ja/commands.md) · [Deutsch](../de/commands.md)

`basalt` sin subcomando inicia `chat`.

| Comando | Qué hace |
|---|---|
| `basalt onboard` | asistente de primera ejecución: elige un modelo para tu máquina y lo descarga |
| `basalt fit` | analiza el hardware y ordena el catálogo de modelos según su compatibilidad |
| `basalt chat --model <id>` | chat interactivo en terminal |
| `basalt serve --model <id> --rest` | servidor REST en `:8080` (compatible con OpenAI y Anthropic) |
| `basalt serve --model <id> --mcp` | servidor MCP stdio para Claude Desktop / Cursor |
| `basalt serve --model <id> --stats` | imprime telemetría en stderr cada 5 s (`--stats-interval`); los mismos valores en `GET /api/v1/stats` y en `status` de MCP |
| `basalt serve --model <id> --canary-minutes 30` | cada 30 min, cuando está inactivo, envía una solicitud de respuesta conocida con prioridad en segundo plano; los conteos de acierto/fallo, salida degenerada y la deriva por modelo de tok/s y aceptación de borradores están bajo `health` en `GET /api/v1/stats` (#325) |
| `basalt models list --author <org>` | explora los modelos de un autor en HuggingFace |
| `basalt models download <repo-id>` | descarga en la caché compartida de HF |
| `basalt models info <repo-id>` | tamaño, cuantización, ventana de contexto |
| `basalt models cache` | qué hay en disco y cuánto espacio ocupa |
| `basalt models check <repo-id>` | comprueba si cabe en memoria (código de salida distinto de cero si no cabe) |
| `basalt models check --deep <repo-id>` | además, antes de descargar: obtiene solo las cabeceras safetensors (unos cientos de KB), construye el modelo solo con formas contra ellas y renderiza la plantilla de chat; lista tensores faltantes, inesperados o con forma incorrecta, un `model_type` no soportado o un error de plantilla, y sale con código distinto de cero |
| `basalt models inspect <repo-id>` | verifica que un modelo en caché esté completo y mide su ancho de bits real |
| `basalt models inspect --verify <repo-id>` | además recalcula el hash de cada archivo en caché frente a su sidecar o al digest del Hub: `true`, `false` o `unknown` por archivo, de solo lectura (#367) |
| `basalt models distill <model> --prompts FILE --teacher-url URL --teacher-model NAME` | destila un modelo profesor detrás de una API en formato OpenAI o Anthropic (`--provider`) en un LoRA para el modelo local; la clave proviene de `BASALT_TEACHER_API_KEY` con `BASALT_TEACHER_URL`; `--budget-usd` se detiene antes de alcanzar un gasto, `--filter verify` conserva solo respuestas que coincidan con el `answer` del prompt, `--on-policy` hace que el estudiante muestree mientras un profesor basalt con el mismo tokenizador puntúa sus tokens en `/v1/score` (KL inversa por token), las ejecuciones offline guardan checkpoint cada `--checkpoint-every` pasos y continúan con `--resume` (#393) |
| `basalt models train-jepa <model> --dataset FILE` | entrena un adaptador LoRA JEPA y un proyector sobre un dataset multivista (una escena por línea JSONL, al menos dos vistas); imprime la pérdida y el rango del embedding antes y después |
| `basalt models convert <source> --out DIR` | Conversor universal any-to-any (#546): recuantiza entre `--to macaq:affine|mxfp4|moe` (Walsh–Hadamard por bloques + refinamiento por inversión Hessiana, MoE de 2.8 bpw ponderado por router #599), `--to flatquant` / `--to lirquant` (#594), `--to sinq` / `a-sinq` / `eaquant` (#561), `--to e8p` (retículo de 2 bits `QuIP#` + `TurboBoA` Babai–LLL, #589), `--experimental-qtip 2.0\|2.5\|3.0` (#494), `nf4`, `SVD-LLM V2` / `OBR` (#592), i-quants nativos `.gguf` y `MACaQ-R`, además de `--pv-tune` (`--pv-preset fast|full`, #545), refinamiento QAT STE consciente del dominio y auditoría poscuantización de calidad/equidad/fugas (`#623`). También disponible vía REST `/v1/models/convert*` y en macOS `ConvertModelSheet` |
| `basalt serve --video-model <id> --rest` | Sirve Video Studio por fases para 24 GB UMA (`LTX-2.5 AV-DiT`, `Kandinsky 6.0`, `LingBot-Video MoE`, `Wan 2.2`) sobre `/v1/videos/*` con 3D-VAE causal, kernel Metal STA y multiplexación `.mp4` mediante `AVAssetWriter` (#608–#611, #614) |
| `basalt review --diff FILE\|- --model <id>` | revisa un diff en el modelo local; `--gitlab` / `--gitea URL --repo R --number N` obtienen un merge request en su lugar, `--post` publica la revisión de vuelta (`GITLAB_TOKEN` / `GITEA_TOKEN`) (#35) |
| `basalt compose` | sirve, planifica, compara diffs, descarga o detiene un sistema YAML multimodelo (`models`, `pipeline`, `pipelines`, `experimental`, `mcp`, `variables`, `profiles`); recarga en caliente modelos, pipelines, presupuestos y ajustes `experimental` activos (`speech_analyzer`, `image_fallback`, `telemetry_confidence_every`, `adaptive_thinking_budget`) mediante `/v1/compose/apply` (#412, #423, #485) |
| `basalt cloud configure` | respaldo en OpenRouter para lo que no cabe en local |
| `basalt cloud cost` | gasto acumulado hasta el momento en el respaldo en la nube |

Dentro de `basalt chat`:

| Entrada | Efecto |
|---|---|
| `/clear` | limpia la conversación y la pantalla |
| `/color`, `/theme` | alterna el tema de colores de la terminal |
| `exit`, `quit` | sale (sin barra) |

Los flags que conviene conocer en `serve`:

| Flag | Por qué usarlo |
|---|---|
| `--reasoning-effort none` | evita que un modelo de razonamiento consuma todo su presupuesto dentro de `<think>` |
| `--reasoning-effort xhigh\|medium\|low` | presupuesto de pensamiento para la familia Qwen |
| `--quant 4bit` | elige una subcarpeta de cuantización en repositorios que distribuyen varias |
| `--kv-bits 4\|8\|auto` | cuantiza la caché KV — libera espacio de generación en una máquina justa de memoria; desactiva la reutilización de prompt-cache. MLX realiza el prefill del prompt en fp16 y lo cuantiza después, por lo que el prompt en sí no puede ser más largo que en fp16 (es más corto: la conversión mantiene brevemente ambas copias). `auto` permanece en fp16, con reutilización de prompt-cache, hasta que el prompt más `max_tokens` de una solicitud no caben, y entonces ejecuta esa solicitud a 8 o, si no, a 4 bits |
| `--kv-bits turbo3\|turbo4\|turbo8v4` | **Experimental** (#471): la caché TurboQuant del fork en capas de atención completa (rotación, libro de códigos Lloyd–Max, una norma por vector; las dos primeras y las dos últimas capas elegibles permanecen en affine de 8 bits). No compatible con `--kv-zones`. Medido en M4 Pro con contexto 8k frente a affine 4-bit: decodificación 8–13% más lenta (Qwen3.8-27B 13.8 vs 15.0 tok/s, LFM2.5-24B 82 vs 94); perplejidad en decodificación sobre 384 tokens +0.3% / +1.3% frente a +1.5% en 4-bit en Qwen3.8, +10.1% / +3.6% frente a +5.0% en LFM2.5; KV a 16k sin reducción (Qwen3.8 460 / 511 MB frente a 461, LFM2.5 118 / 131 frente a 97, Gemma 4 26B-A4B 423 frente a 306). La compresión se aplica en decodificación: un bloque multitoken lee las claves sin comprimir |
| `--kv-bits polar4` | **Experimental** (#351), con `--kv-zones`: la zona intermedia por zonas almacena los pares RoPE de cada clave en un byte (fase de 5 bits, módulo de 3 bits sobre cuantiles de Rayleigh escalados por cabeza y par a partir del primer lote de migración) y sus demás dimensiones en affine de 4 bits; los valores permanecen en affine de 4 bits. Solo Qwen3, Qwen3.5 y LFM2, cuyo RoPE empareja las dimensiones i e i + d/2; cualquier otro modelo mantiene claves affine y lo registra en el log. Medido en M4 Pro, 256 tokens decodificados tras 8k, frente a q4 y k8v4 por zonas: perplejidad Qwen3.8-27B 8.61 vs 8.56 / 8.50, LFM2.5-24B 61.2 vs 76.5 / 70.9 (una muestra ruidosa de 256 tokens); KV por zonas 196 vs 197 / 255 MB y 59 vs 62 / 80 MB; decodificación 12.4 vs 14.0 / 14.6 tok/s y 11.3 vs 19.5 / 18.2 (la zona intermedia se decodifica a fp16 en cada paso, no hay kernel polar); se encontró un passkey de 16k a profundidades 0.2 y 0.8 en ambos modelos. El prototipo offline midió que polar no supera a affine a igualdad de bits |
| `--kv-bits k8v4` | con `--kv-zones`: la zona intermedia cuantizada almacena claves a 8 bits y valores a 4 (13 bits por par K+V con escalas de grupo, 0.41× fp16, entre el 0.53× de 8 bits y el 0.28× de 4 bits). `auto` con `--kv-zones` lo intenta entre 8 y 4 bits. En un modelo al que no aplican las zonas (Gemma 4) se ejecuta como 8 bits uniforme. **Experimental:** `k8v4h` también aplica una transformada de Walsh–Hadamard a los valores antes de la cuantización de 4 bits (y su inversa al leer), para repartir canales con valores atípicos; solo bajo activación explícita, `auto` nunca lo elige. Medido con 8k tokens evaluados tras un contexto de 8k, perplejidad frente a `k8v4`: Qwen3-4B 6.568 vs 6.562, Ornith-1.5-9B 4.937 vs 4.920, LFM2.5-8B 8.723 vs 8.750 (una ejecución cada uno, dentro del ruido), y el pico de memoria tras un prompt de 16k subió unos 85 MB en Ornith y 30–150 MB en Qwen3-4B (la copia en fp32 de los valores que rota). Rota dimensiones de cabeza 2^k y 12·2^k, donde la transformada de MLX es su propia inversa; otras dimensiones de cabeza quedan sin rotar, y `serve` lo registra al cargar. Podría importar en contextos más largos (32k+) o en modelos con canales atípicos en V; eso no está probado |
| `--kv-zones` | con `--kv-bits`: mantiene los primeros 64 y los últimos 1024 tokens de cada capa de atención completa en fp16 y cuantiza solo los tokens intermedios, a medida que se hace el prefill del prompt. No hay prefill fp16 que convertir, así que el prompt puede usar todo el espacio cuantizado y baja el pico de memoria; en Qwen3-4B, 8k tokens evaluados tras un contexto de 8k, la perplejidad a 4 bits es 6.58 frente a 6.56 en fp16 y 8.66 en 4 bits uniforme |
| `--kv-evict F` | **Experimental**, con `--kv-zones`: descarta la fracción `F` (0–0.9) de la zona intermedia cuantizada de cada capa de atención completa conforme los tokens salen de la ventana reciente, por cada cabeza KV aquellos cuyas claves tienen la mayor norma L2 (arXiv:2406.11430). No necesita pesos de atención, por lo que la atención sigue en los kernels fusionados; los sinks y la ventana reciente nunca se descartan, y el espacio que reportan `serve` y `models check` cuenta solo los tokens conservados. Tras un prompt de 16k con k8v4, la KV en Qwen3-4B baja de 1.11 GB a 0.89 GB en 0.25 y a 0.66 GB en 0.5. Tiene un coste en calidad: perplejidad (8k evaluados tras 8k) 6.71 / 7.04 frente a 6.56 en Qwen3-4B, 9.06 / 9.52 frente a 8.75 en LFM2.5-8B, sin cambios en Ornith-1.5-9B; se perdió un passkey de 16k en una de cinco profundidades en Qwen3-4B y Ornith a 0.25, y la salida greedy diverge de fp16 desde los primeros tokens. Gemma 4, y cualquier modelo que realice el prefill de más de la ventana reciente en una sola pasada (comprobado al cargar), conservan cada token y se dimensionan así |
| `--kv-head-split R` | **Experimental**, incompatible con `--kv-bits` uniforme: mantiene el contexto completo solo en la fracción `R` (0.05–1) de cabezas KV que leen hechos de la parte media de un prompt largo, puntuadas una vez por modelo sobre un conjunto sintético de passkeys (DuoAttention, cacheado en `~/.basalt/head-scores`); las demás cabezas conservan 128 tokens sink y 256 recientes. En Qwen3-4B a 32k con `R` 0.25: KV 4.76 → 1.26 GB, decodificación 27.2 → 36.2 tok/s, passkey 10/10 a 16k y 32k. Se rechaza, con una advertencia, en la familia Qwen3.5 y los híbridos LFM2 / Nemotron-H y en modelos cuya atención no pasa por la caché (Gemma 4). En los híbridos, el 25% elegido por ablación perdió el passkey a 16k (Qwen3.8-27B 0/3 profundidades, LFM2.5-24B 2/3) y elevó la perplejidad un 24% y un 42%; elegir cabezas por fidelidad de salida corresponde a #282. Con `--kv-zones --kv-bits k8v4` (experimental, desactivado salvo que se especifiquen ambos) las cabezas conservadas almacenan su contexto largo por zonas: los primeros 64 y últimos 1024 tokens exactos, y la parte media con claves a 8 bits y valores a 4; las demás cabezas se mantienen como arriba. Al igual que `--kv-zones`, se aplica a solicitudes sin espacio de nombres en prompt-cache |
| `--prompt-cache-mb N` | memoria reservada para el árbol de prefijos del prompt-cache (por defecto: la mitad de lo que deja el conjunto de trabajo GPU recomendado por Metal tras los pesos, registrado al cargar; `0` lo desactiva), ver más abajo |
| `--prompt-cache-disk-mb N` | persiste la caché de prompts en `~/.basalt/prompt-cache/` (`--prompt-cache-dir`) al apagar ordenadamente, antes de un cambio de modelo y al salir de `basalt chat`, de modo que una sesión reanudada o un servidor reiniciado restaure su prefijo desde disco en lugar de hacer prefill de nuevo (por defecto `0`, desactivado). Las ramas más usadas se escriben primero, hasta `N` MB y solo aquellas cuya escritura quepa dentro del plazo de cierre asumiendo 1 GB/s; una ruta más larga de la misma conversación sustituye a los archivos más cortos que cubre, los archivos usados menos recientemente se eliminan para hacer sitio, los archivos sin usar durante `--prompt-cache-disk-days` (7) se borran al inicio, y `basalt sessions prune` hace lo mismo offline. El directorio debe ser nuevo, estar vacío o ser un directorio de prompt-cache previo (uno con otros archivos se rechaza). Un archivo solo lo usa el mismo modelo (blobs de pesos, o contenido muestreado de pesos fuera de la caché de HF, config, tokenizador y plantilla de chat), versión de basalt y formato de caché; cualquier otra cosa, un archivo truncado o una disposición de capas distinta recurre a un prefill normal. Requiere `--session-log full` (los archivos guardan la conversación como tensores KV) y el prompt-cache en memoria; `--kv-bits`, `--kv-zones` y los prompts multimodales nunca se persisten |
| `--cache-blend` | reutiliza bloques de prompt en caché en cualquier orden, de forma aproximada (CacheBlend); `--cache-blend-ratio R` fija la proporción recalculada (por defecto 0.3), ver más abajo |
| `--min-p`, `--top-k`, `--seed` | muestreo; `--seed` hace reproducible una ejecución no greedy; el `min_p` de una solicitud sobrescribe `--min-p` |
| `--max-tokens` | límite superior de generación por defecto (2048–128000) |
| `--dry-run` | comprobación de viabilidad en memoria y salida sin cargar el modelo |
| `--config basalt.yaml` | opciones de `serve` desde un archivo YAML: las claves bajo `defaults.{model,serve,mcp}` se convierten en los flags equivalentes, los flags en línea de comandos prevalecen y las claves desconocidas se reportan con línea y columna (#344) |
| `--mcp-enable <tool\|group>`, `--mcp-disable <tool\|group>` | con `--mcp`, activa o desactiva selectivamente herramientas MCP individuales o grupos (`serving`, `gemma`, `media`, `harness`, `xray`, `surgery`, `research`, `all`) sin exponer toda la superficie `--research-tools`; `--mcp-disable` siempre prevalece sobre `--mcp-enable` y `--research-tools`, y los nombres desconocidos fallan rápido al arrancar. También `defaults.mcp.enable` / `defaults.mcp.disable` en `basalt.yaml` (#484) |
| `--adapter name=dir` | carga un adaptador LoRA de mlx-lm sobre el modelo base residente (repetible); una solicitud selecciona uno con `X-Basalt-Adapter: name`. Las solicitudes del mismo adaptador se ejecutan juntas, un cambio espera a las generaciones en curso, cada adaptador tiene su propio espacio de nombres en prompt-cache; un adaptador cuyos tensores no encajan en ninguna capa de la base se rechaza al arrancar (#179) |
| `--experimental-zero-copy-body` | **Experimental**: envuelve el cuerpo de cada solicitud REST en `Data` sin copiarlo. En Gemma 4 26B-A4B con 1–8 imágenes, el pico de memoria del proceso es 70–95 MB menor; el TTFT no mejora (#345) |
| `--experimental-smallm-kernel` | **Experimental**, desactivado por defecto (igual que `BASALT_SMALLM_KERNEL=1`): pasadas forward de 4–8 filas de capas lineales affine de 4 bits (ventanas de verificación de speculative-lookup y MTP, decodificación por lotes) se ejecutan con el kernel simdgroup-matrix de basalt, que decodifica cada peso una vez para todas las filas. M4 Pro, formas de Qwen3.8-27B: 1.5–1.7× del tiempo de un token para cualquier cantidad entre 4 y 8 filas, donde el kernel estándar tarda 1.7–1.9× con 4 y 3.3–3.7× con 8; las salidas difieren del estándar por redondeo bf16, así que la identidad greedy en modelos reales aún no está verificada (#208) |
| `--experimental-adaptive-thinking-budget` | **Experimental**, desactivado por defecto: una solicitud que no define ni `thinking_budget` ni `reasoning_effort` recibe un presupuesto de pensamiento a partir de una estimación de dificultad de su último mensaje de usuario (palabras clave como "prove" o "algorithm", longitud, herramientas): fácil 512 tokens, medio 2048, difícil sin límite. Solo modelos de razonamiento con transición de presupuesto (Qwen3.x, LFM2.5); sin medir hasta que aterrice la ejecución de #41 |
| `--require-verified` | antes de cargar, recalcula el hash de la instantánea frente a sus sidecars o los digests del Hub y rehúsa arrancar ante cualquier archivo no verificado (#367) |
| `--port`, `--host` | por defecto `127.0.0.1:8080`; cualquier otro host necesita una clave API (`BASALT_API_KEY` o `--auto-generate-key`) |
| `virtual_keys` (solo configuración) | claves API adicionales con su propio presupuesto en la nube: `"virtual_keys": [{"key": "vk-…", "id": "team-a", "max_budget": 2.0}]` en `~/.gem/config.json`; una clave tiene al menos 16 caracteres, los ids y claves son únicos; el gasto por clave sobrevive a los reinicios |
| `--expert-streaming`, `--no-expert-streaming` | transmite pesos Mixture-of-Experts enrutados desde fragmentos safetensors en SSD (lecturas asíncronas por lotes `F_NOCACHE` hacia ranuras LRU fijas, `--expert-cache-gb` por defecto 25% de los pesos de expertos). Se habilita automáticamente cuando un checkpoint local apilado `SwitchLinear` cae en el nivel de ajuste `Streaming` (`weights > workingSetBudget` mientras los pesos residentes + caché de expertos caben); desactívalo con `--no-expert-streaming` o `BASALT_NO_EXPERT_STREAMING=1` (`--experimental-expert-streaming` se mantiene como alias, #225, #226) |
| `--speech-analyzer` | sirve `/v1/audio/transcriptions`, `basalt_transcribe` y audio en `/v1/pipeline` mediante `SpeechAnalyzer` de macOS en el Neural Engine cuando no hay un codificador de audio dedicado cargado (alias `--experimental-speech-analyzer`, #222, #226, #230) |
| `--ane-vision-tower DIR` | ejecuta el codificador de visión de PaddleOCR-VL en el Neural Engine desde un paquete Core AI (`metadata.json` + `tower.aimodel`), persistiendo marcadores de artefactos especializados y metadatos bajo `~/.basalt/cache/coreai-vision/` indexados por SHA-256 del paquete y compilación de macOS (alias `--experimental-ane-vision-tower`, #224, #226, #400) |
| `--max-concurrent N`, `--max-queue N` | generaciones decodificando a la vez (por defecto 1; cada una mantiene su propia caché KV) y solicitudes esperando turno (por defecto 8), por prioridad — primero `basalt chat`, luego solicitudes de servicio (títulos, resúmenes) y sondas de harness, después tráfico de API y luego benchmarks — y por orden de llegada dentro de cada nivel; una solicitud de mayor prioridad que encuentre la cola llena desplaza al solicitante en espera de menor prioridad; más allá de la cola el servidor responde 503 con `Retry-After` (un stream que ya envió sus cabeceras recibe en su lugar un evento de error). Un cambio de modelo espera a las generaciones en curso y las nuevas solicitudes se encolan detrás; dos cargas del mismo modelo comparten una sola, mientras tanto la carga de otro modelo devuelve 503. Ante SIGTERM/SIGINT las generaciones disponen de 5 s para terminar y luego se cancelan para que el proceso salga |
| `--batch-slots N` | con `--max-concurrent` 2 o más, hasta N generaciones decodifican juntas en una sola pasada forward por lotes (por defecto 1, desactivado). Soporta capas de atención completa, estado recurrente y ventana deslizante (Qwen3 denso/MoE, híbridos Qwen3.5/3.8 y Nemotron-H, LFM2, Gemma 4: las filas comparten un anillo de la ventana, rellenado por la izquierda y enmascarado como las filas de atención completa, #255) tanto con KV fp16 (`BatchKVCache`) como con `--kv-bits` affine uniforme (`4`, `8`, o `auto` en el mismo escalón vía `BatchQuantizedKVCache`, #243), además de máscaras gramaticales por fila de `response_format` / herramienta forzada; las solicitudes que usan `--kv-zones`, `k8v4`, `polar4`, `turbo*`, avance rápido gramatical, prompt lookup, MTP, CacheBlend o adjuntos multimedia decodifican en solitario como antes (ver matriz abajo). El prefill y la caché de prompts no cambian; cada fila conserva su propio muestreador, tokens de parada y `max_tokens`. La salida greedy por lotes iguala a la individual en calidad, no bit a bit: MLX elige otros kernels para una fila que para varias (matmul cuantizado), y una fila con relleno a la izquierda por un vecino más largo lee sus claves en otro orden, de modo que qué filas comparten un paso puede invertir un empate cercano (#319). Las filas que no se añaden relleno entre sí dejan intactos los logits de las demás |
| `--session-log full\|meta\|off` | registro JSONL local de sesiones bajo `~/.basalt/sessions/<date>/<session>.jsonl` (`0700`/`0600`): una línea `request` antes de la llamada al motor y una línea `response` después (estado, tokens, tiempos, memoria, motivo de fin) para cada endpoint, más líneas `error` para solicitudes rechazadas (solo tamaño, nunca el cuerpo ni las cabeceras) y `model_switch`. `full` (por defecto) también guarda la conversación y la respuesta, `meta` solo tamaños y hashes SHA-256; `--session-log-dir`, `--session-log-retention-days` (14), `--session-log-max-total-mb` (1024); la sesión se nombra mediante `X-Basalt-Session` (o `x-session-id`); sin uno, una solicitud que amplía una conversación anterior se une a su sesión y cualquier otra inicia una nueva. Un id conocido añade al archivo existente tras un reinicio del servidor (`session_resume`), y una sesión inactiva durante `--session-idle-minutes` (30) se suspende. `basalt sessions list \| show <id\|latest> \| stats <id\|latest>` lee los archivos sin cargar ningún modelo; `basalt chat` mantiene un historial multiturno en su propia sesión y `basalt chat --resume <id\|latest>` lo continúa (no disponible para sesiones `meta`). En modo `full`, bloques de clave privada y tokens API (`sk-`, `ghp_`/`github_pat_`, `AKIA`, `xox*-`, `Bearer`) se reemplazan por `[REDACTED:*]` (mejor esfuerzo, sin garantía; `--session-log-redact off`), y una solicitud que amplía una anterior de la sesión almacena solo sus nuevos mensajes más `parent` y `prefix_count` |
| `--rate-limit N` | solicitudes por minuto en todo el servidor, 429 más allá de ese límite — desactivado por defecto en loopback, 120 en otro caso; `0` lo desactiva; también `rate_limit` en `~/.gem/config.json` |
| `--allow-origin URL` | origen de navegador (`https://app.example:3000`, o una interfaz local como `http://localhost:3000`) autorizado a llamar a la API además del propio servidor; repetible; también `allowed_origins` en `~/.gem/config.json` |
| `--cloud-fallback MODEL` | responde desde un modelo en un servidor compatible con OpenAI cuando el modelo local no puede: la KV de la solicitud no cabe en el presupuesto de memoria de generación (el mismo espacio KV que limita `max_tokens`), el prompt supera `--local-context-limit N`, o el router de coste evalúa la tarea por encima del modelo local y la ganancia compensa el precio. `--cloud-base-url URL` elige el servidor (por defecto OpenRouter; cualquier endpoint `/v1` como vLLM, Ollama, LM Studio u otro Mac, sin clave necesaria allí); `--no-cloud-fallback` lo desactiva. También `cloud_fallback` en `~/.gem/config.json`: `{"enabled": true, "base_url": "http://192.168.1.20:8000/v1", "model": "qwen3-235b", "api_key_env": "LAN_KEY", "local_context_limit": 32768}`; `enabled: false` lo mantiene desactivado. La clave de OpenRouter solo se envía a openrouter.ai. El gasto está topado por los presupuestos diarios/mensuales de `basalt cloud configure`, por `cloud_fallback.session_budget` (USD por `x-session-id`) y por el `max_budget` de cada clave virtual; superado el presupuesto, no se llama a la nube. `--router-params FILE` (parámetros entrenados Bradley–Terry: `strongEmbedding`, `weakEmbedding`, `weights`, `projection`) activa la comprobación de capacidad, ajustada mediante `--cost-threshold θ` (por defecto 0.5) y `--cache-stickiness λ` (por defecto 0.1; un `x-session-id` caliente conserva su lado hasta que el margen supere λ veces el coste de cambio); también `router_params`, `cost_threshold`, `cache_stickiness` en `cloud_fallback`. Las solicitudes con herramientas o `response_format` y las solicitudes de servicio permanecen en local; una llamada fallida a la nube se responde localmente |

**Matriz de capacidades de decodificación por lotes (`--batch-slots N`, #240, #243, #255).** Cada solicitud elegible hace prefill individualmente y luego reclama un puesto en `BatchedDecoder` cuando su disposición de caché y ancho de bits KV activo coinciden con el lote en ejecución; las solicitudes no elegibles o incompatibles recurren de forma transparente a decodificación individual serializada bajo `ModelEvaluationLock`:

| Dimensión | Soportado en `BatchedDecoder` | Alternativa en solitario |
|---|---|---|
| Familias de modelos | Llama, Qwen3 (denso y MoE), MiniMax-M2 (`BatchKVCache` / `BatchQuantizedKVCache`); híbridos Qwen3.5/3.6/3.8, Nemotron-H, LFM2/LFM2.5 (+ `ArraysCache`); Gemma 4 denso y MoE (+ `BatchRotatingKVCache` y capas con KV compartida); turnos solo de texto en PaddleOCR-VL / DeepSeek-OCR | Gemma 3 (`RotatingKVCache` con prefijo fijado / disposición no verificada), `model_type` no verificado |

**Reutilización de prompt-cache.** El servidor conserva la caché KV del modelo para prompts recientes en un árbol de prefijos: los prompts que empiezan con los mismos tokens comparten una única copia almacenada de ese inicio, y una solicitud solo hace prefill de lo que sigue al prefijo más largo almacenado. Así, el siguiente turno de una conversación cuesta únicamente sus tokens nuevos (un resultado de herramienta añadido a un largo historial de agente, no todo el historial otra vez), y una segunda conversación que abre con el mismo system prompt y herramientas — un subagente de Claude Code, otro hilo de Codex — parte de la porción compartida en vez de volver a hacer su prefill. La coincidencia es por tokens, así que no hace falta un id de conversación (`prompt_cache_key`, `metadata.user_id` y `x-session-id` se ignoran); un cliente que quiera mantener sus prompts separados envía `X-Basalt-Cache-Key: <name>` (1-256 bytes, en cualquier endpoint de generación) y obtiene su propio árbol, que comparte el presupuesto de bytes pero ningún prefijo con el árbol compartido ni con otras claves; los títulos y demás solicitudes de servicio nunca tocan la caché. Bajo el presupuesto `--prompt-cache-mb`, la rama menos usada recientemente se recorta por su extremo (la rama de instantánea de un modelo híbrido, ver abajo, se elimina entera, ya que su estado recurrente solo es válido al final), de manera que una conversación inactiva conserva su system prompt y herramientas durante más tiempo, y el nodo hasta el que reutiliza una solicitud en curso nunca se expulsa (para un modelo híbrido es su nodo de instantánea; la solicitud tiene su propia copia de los datos, así que expulsar el resto de su rama no puede afectarla); el árbol también mantiene como máximo 4096 ramas, descartando la libre menos usada recientemente por encima de ese límite. Los contadores de uso reportan lo que realmente se reutilizó: `prompt_tokens_details.cached_tokens` (Chat Completions), `input_tokens_details.cached_tokens` (Responses), `cache_read_input_tokens` (Anthropic, donde `input_tokens` cuenta solo el resto sometido a prefill). Los modelos híbridos de atención/SSM como Qwen3.5/3.6 y Ornith-1.5, y Gemma 4 con sus capas de ventana deslizante, también reutilizan el turno anterior de una conversación: su estado recurrente o rotatorio no puede rebobinarse, así que al hacer prefill de un prompt el servidor guarda una instantánea del mismo al final del texto de la solicitud, antes de los tokens de cierre de la plantilla de chat, y el siguiente turno que amplía ese texto restaura la instantánea y hace prefill solo de lo que sigue (Ornith-1.5-9B, prompt de agente de 12.6k tokens: el segundo turno tarda alrededor de 1 s en lugar de unos 36 s). Un turno reutilizado puede diferir de una ejecución sin caché después de sus primeros tokens: el prefill se trocea de forma distinta, lo que desplaza ligeramente los resultados en bf16 (medido en Ornith: el estado restaurado es bit a bit igual a un prefill desde cero cortado en los mismos puntos, y difiere de un prefill en una sola fase en como máximo 1.56 en los logits de la última posición con el mismo top 5; en Gemma 4 12B la caché restaurada también es bit a bit igual, y a lo largo de una sesión de doce turnos de ~4k tokens difiere de un prefill en una sola fase en 0.60–2.33 con el mismo token greedy, casi tanto como un prefill en una fase en bloques de 256 tokens en vez de 512 difiere de sí mismo, 2.53, así que a temperatura 0 un token cercano al empate aún puede cambiar). Solo reutilizan desde una instantánea así, por lo que una segunda conversación con el mismo system prompt hace el prefill completo. `--kv-bits` siempre hace el prefill del prompt completo.

**CacheBlend (opcional, aproximado).** El árbol de prefijos solo ayuda cuando un prompt empieza de la misma manera; un agente que pega los mismos archivos en otro orden vuelve a hacer el prefill de todos ellos. `--cache-blend` guarda también la KV de cada bloque del prompt — un bloque termina tras cada línea en blanco, tanto si el tokenizador la escribe como un token o como dos tokens de salto de línea, de modo que archivos y mensajes separados por líneas en blanco conservan sus propios bloques; los bloques de menos de 16 tokens siempre se recalculan — y reutiliza un bloque allá donde aparezca en un prompt posterior (las claves se guardan antes de RoPE y se rotan a la nueva posición). Los bloques en caché se calcularon junto a otro texto, así que su KV está desactualizada: siguiendo CacheBlend (arXiv:2405.16444), la primera capa se recalcula para cada token, y solo `--cache-blend-ratio` de los tokens reutilizados (por defecto 0.3), más cada token que no está en el almacén, se recalculan en las capas posteriores. El presupuesto va primero a los primeros 32 tokens de cada bloque reutilizado, cuyo contexto cambió más al moverse el bloque (como en EPIC, arXiv:2410.15332), ordenados por cuánto se desvía su KV en la segunda capa, y solo después a los tokens con mayor desviación del resto. La pasada forward mezclada cuesta aproximadamente 1.2× del prefill propio del modelo por token recalculado, de modo que un prompt solo se mezcla cuando (1 − ratio) × la proporción de tokens reutilizados es al menos 0.2, y solo mientras toda la caché se mantenga dentro de 16 384 tokens; de lo contrario — un prompt nuevo, poca reutilización, `--cache-blend-ratio 1`, un contexto largo — toma el prefill por bloques propio del modelo y sus bloques se almacenan a partir de esa caché (las claves se desrotan desde post-RoPE, exacto hasta el redondeo del dtype de la caché, ~2⁻⁸ relativo en bf16). El resultado es aproximado. Medido en Qwen3-4B-4bit (M4 Pro) con seis archivos congelados de 550–900 tokens (`benchmarks/cacheblend`) en cuatro órdenes nuevos, cada uno con una pregunta nueva (4 854 de ~5 066 tokens procedentes de bloques), evaluando la respuesta greedy del prefill completo (50 tokens) bajo teacher forcing — log-prob medio de los tokens de referencia y coincidencia top-1 por posición, en esta muestra de 200 posiciones (0.01 equivale a dos posiciones):

| caché | log-prob | top-1 | perplejidad |
|---|---|---|---|
| prefill completo | −0.094 | 0.995 | 1.099 |
| ratio 0 | −0.180 | 0.925 | 1.198 |
| ratio 0.15 (el valor del artículo) | −0.166 | 0.945 | 1.181 |
| **ratio 0.3 (por defecto)** | −0.123 | 0.960 | 1.131 |
| ratio 0.5 | −0.125 | 0.970 | 1.134 |
| ratio 1 (prefill nativo) | −0.094 | 0.995 | 1.099 |

Recalcular primero las cabeceras de bloque es lo que convierte a 0.3 en el valor por defecto: solo con la desviación de la capa 1, ratio 0.3 dejaba una brecha de perplejidad de 0.085 e incluso 0.5 dejaba 0.038; con las cabeceras de bloque primero, 0.3 deja 0.032 (0.50: 0.035). En otros cuatro órdenes y preguntas de los mismos archivos la brecha es mayor (0.096 con 0.3, frente a 0.169 sin cabeceras de bloque y 0.120 para el antiguo valor por defecto 0.5), de modo que la cota de 0.05 se cumple en la muestra del benchmark, no en todo prompt. `--cache-blend-ratio 0` intercambia calidad por el prefill más corto. Solo modelos densos de las familias Llama y Qwen3; los demás modelos mantienen la ruta exacta de prefijos. Con el flag activo, el presupuesto de prompt-cache se divide a la mitad entre el árbol y el almacén de bloques. `cached_tokens` sigue contando solo los tokens exactos del árbol de prefijos; los tokens mezclados se cuentan en `prompt_tokens` y se registran en el log (`[CacheBlend] Blended N prompt tokens: R from cached chunks, X of them recomputed`), y el árbol solo guarda la cabeza exacta de un prompt mezclado. Una pasada mezclada mantiene brevemente a la vez la caché ensamblada y las claves y valores sin rotar de los bloques (alrededor del doble de la KV del prompt, p. ej., ~5 GB para 16k tokens de Qwen3-4B), lo cual no está incluido en las estimaciones de memoria. Con ratios pequeños domina el coste fijo de las capas 0–1 y de la pasada de desviación, por lo que 0.15 y 0.3 son más lentos de lo que sugiere el modelo lineal de coste. Desactivado por defecto porque modifica las salidas; `--prompt-cache-mb 0` también lo desactiva.

Privacidad: todos los clientes comparten un mismo árbol de prefijos, y `cached_tokens` revela cuántos tokens iniciales comparte un prompt con prompts anteriores, de modo que un invocador puede sondear qué envió otro cliente. En un servidor compartido por personas que no deben ver los prompts de otras, ejecuta con `--prompt-cache-mb 0`; con `--cache-blend`, el tiempo hasta el primer token también muestra qué bloques envió otro cliente.
