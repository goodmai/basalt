# Commandes

`basalt` sans sous-commande lance `chat`.

| Commande | Ce qu'elle fait |
|---|---|
| `basalt onboard` | assistant de premier lancement : choisit un modèle adapté à votre machine et le télécharge |
| `basalt fit` | analyse le matériel et classe le catalogue de modèles en fonction de celui-ci |
| `basalt chat --model <id>` | discussion interactive dans le terminal |
| `basalt serve --model <id> --rest` | serveur REST sur :8080 (compatible OpenAI + Anthropic) |
| `basalt serve --model <id> --mcp` | serveur MCP stdio pour Claude Desktop / Cursor |
| `basalt serve --model <id> --stats` | affiche la télémétrie sur stderr toutes les 5 s (`--stats-interval`) ; les mêmes valeurs sont exposées sur `GET /api/v1/stats` et dans `status` côté MCP |
| `basalt serve --model <id> --canary-minutes 30` | toutes les 30 min, lorsqu'il est inactif, envoie une requête à réponse connue en priorité d'arrière-plan ; les succès/échecs, le nombre de sorties dégénérées ainsi que la dérive par modèle des tok/s et du taux d'acceptation du brouillon figurent sous `health` dans `GET /api/v1/stats` (#325) |
| `basalt models list --author <org>` | parcourt les modèles d'un auteur HuggingFace |
| `basalt models download <repo-id>` | télécharge dans le cache HF partagé |
| `basalt models info <repo-id>` | taille, quantification, fenêtre de contexte |
| `basalt models cache` | liste ce qui se trouve sur le disque et l'espace occupé |
| `basalt models check <repo-id>` | vérifie s'il tient en mémoire (code de sortie non nul dans le cas contraire) |
| `basalt models check --deep <repo-id>` | également, avant le téléchargement : récupère uniquement les en-têtes safetensors (quelques centaines de Ko), construit le modèle en forme uniquement (*shape-only*) à partir de ceux-ci et effectue le rendu du modèle de discussion (*chat template*) ; liste les tenseurs manquants, inattendus ou de forme incorrecte, un `model_type` non pris en charge ou une erreur de modèle (*template*), et quitte avec un code de sortie non nul |
| `basalt models inspect <repo-id>` | vérifie qu'un modèle en cache est complet et mesure sa largeur de bits réelle |
| `basalt models inspect --verify <repo-id>` | recalcule également le hachage de chaque fichier en cache par rapport à son fichier compagnon (*sidecar*) ou au condensat (*digest*) du Hub : `true`, `false` ou `unknown` par fichier, en lecture seule (#367) |
| `basalt models distill <model> --prompts FILE --teacher-url URL --teacher-model NAME` | distille un enseignant derrière une API au format OpenAI ou Anthropic (`--provider`) vers un LoRA pour le modèle local ; la clé provient de `BASALT_TEACHER_API_KEY` avec `BASALT_TEACHER_URL` ; `--budget-usd` arrête l'exécution avant d'atteindre une dépense, `--filter verify` ne conserve que les réponses correspondant au champ `answer` de l'invite, `--on-policy` fait échantillonner l'élève tandis qu'un enseignant basalt partageant le même tokenizer évalue ses jetons sur `/v1/score` (KL inverse par jeton) ; les exécutions hors ligne créent un point de contrôle toutes les `--checkpoint-every` étapes et reprennent avec `--resume` (#393) |
| `basalt models train-jepa <model> --dataset FILE` | entraîne un adaptateur LoRA JEPA et un projecteur sur un jeu de données multi-vues (une scène par ligne JSONL, au moins deux vues) ; affiche la perte et le rang des plongements avant et après |
| `basalt models convert <source> --out DIR` | convertisseur universel tout-en-tout (#546) : requantifie avec `--to macaq:affine|mxfp4|moe` (transformée de Walsh–Hadamard par blocs + raffinement par retournement hessien, MoE pondéré par le routeur à 2.8 bpw #599), `--to flatquant` / `--to lirquant` (#594), `--to sinq` / `a-sinq` / `eaquant` (#561), `--to e8p` (réseau 2 bits `QuIP#` + `TurboBoA` Babai–LLL, #589), `--experimental-qtip 2.0\|2.5\|3.0` (#494), `nf4`, `SVD-LLM V2` / `OBR` (#592), i-quants natifs `.gguf` et `MACaQ-R`, plus `--pv-tune` (`--pv-preset fast|full`, #545), raffinement QAT STE sensible au domaine et audit de qualité/équité/fuite post-quantification (`#623`). Également disponible via REST `/v1/models/convert*` et macOS `ConvertModelSheet` |
| `basalt serve --video-model <id> --rest` | sert le Studio Vidéo phasé sur UMA 24 GB (`LTX-2.5 AV-DiT`, `Kandinsky 6.0`, `LingBot-Video MoE`, `Wan 2.2`) sur `/v1/videos/*` avec 3D-VAE causal, noyau Metal STA et multiplexage `.mp4` `AVAssetWriter` (#608–#611, #614) |
| `basalt review --diff FILE\|- --model <id>` | relit un diff sur le modèle local ; `--gitlab` / `--gitea URL --repo R --number N` récupèrent plutôt une merge request, `--post` publie la revue en retour (`GITLAB_TOKEN` / `GITEA_TOKEN`) (#35) |
| `basalt compose` | sert, planifie, compare (`diff`), récupère (`pull`) ou arrête un système YAML multi-modèles (`models`, `pipeline`, `pipelines`, `experimental`, `mcp`, `variables`, `profiles`) ; recharge à chaud les modèles, pipelines, budgets et paramètres `experimental` actifs (`speech_analyzer`, `image_fallback`, `telemetry_confidence_every`, `adaptive_thinking_budget`) via `/v1/compose/apply` (#412, #423, #485) |
| `basalt cloud configure` | repli OpenRouter pour ce qui ne tient pas localement |
| `basalt cloud cost` | dépenses cumulées à ce jour sur le repli cloud |

Dans `basalt chat` :

| Entrée | Effet |
|---|---|
| `/clear` | efface la conversation et l'écran |
| `/color`, `/theme` | fait défiler les thèmes de couleurs du terminal |
| `exit`, `quit` | quitte (sans barre oblique) |

Les options utiles à connaître sur `serve` :

| Option | Pourquoi l'utiliser |
|---|---|
| `--reasoning-effort none` | empêche un modèle de raisonnement de dépenser tout le budget à l'intérieur de `<think>` |
| `--reasoning-effort xhigh\|medium\|low` | budget de réflexion pour la famille Qwen |
| `--quant 4bit` | choisit un sous-dossier de quantification dans les dépôts qui en fournissent plusieurs |
| `--kv-bits 4\|8\|auto` | quantifie le cache KV — libère de l'espace de génération sur une machine limitée en mémoire ; désactive la réutilisation du cache d'invite. MLX pré-remplit (*prefill*) l'invite en fp16 puis la quantifie ensuite, de sorte que l'invite elle-même n'est pas plus longue qu'en fp16 (plus courte : la conversion conserve brièvement les deux copies). `auto` reste en fp16, avec réutilisation du cache d'invite, jusqu'à ce que l'invite d'une requête plus `max_tokens` ne tienne plus en mémoire, puis exécute cette requête en 8 bits, sinon en 4 bits |
| `--kv-bits turbo3\|turbo4\|turbo8v4` | **Expérimental** (#471) : le cache TurboQuant du fork sur les couches d'attention complète (rotation, dictionnaire Lloyd–Max, une norme par vecteur ; les deux premières et les deux dernières couches éligibles restent en 8 bits affine). Incompatible avec `--kv-zones`. Mesuré sur M4 Pro à un contexte de 8k par rapport à l'affine 4 bits : décodage 8–13% plus lent (Qwen3.8-27B 13.8 contre 15.0 tok/s, LFM2.5-24B 82 contre 94) ; perplexité au décodage sur 384 jetons +0.3% / +1.3% contre +1.5% pour le 4 bits sur Qwen3.8, +10.1% / +3.6% contre +5.0% sur LFM2.5 ; KV à 16k pas plus petit (Qwen3.8 460 / 511 MB contre 461, LFM2.5 118 / 131 contre 97, Gemma 4 26B-A4B 423 contre 306). La compression s'applique au décodage : un bloc multi-jetons lit les clés brutes |
| `--kv-bits polar4` | **Expérimental** (#351), avec `--kv-zones` : la zone centrale stocke chaque paire RoPE de clés sur un octet (phase sur 5 bits, module sur 3 bits selon des quantiles de Rayleigh mis à l'échelle par tête et par paire à partir du premier lot de migration) et ses autres dimensions en affine 4 bits ; les valeurs restent en affine 4 bits. Uniquement Qwen3, Qwen3.5 et LFM2, dont le RoPE associe les dimensions i et i + d/2 ; tout autre modèle conserve des clés affines et le journalise. Mesuré sur M4 Pro, 256 jetons décodés après 8k, face au q4 zoné et au k8v4 : perplexité Qwen3.8-27B 8.61 contre 8.56 / 8.50, LFM2.5-24B 61.2 contre 76.5 / 70.9 (un échantillon bruité de 256 jetons) ; KV zoné 196 contre 197 / 255 MB et 59 contre 62 / 80 MB ; décodage 12.4 contre 14.0 / 14.6 tok/s et 11.3 contre 19.5 / 18.2 (la zone centrale est décodée en fp16 à chaque étape, il n'y a pas de noyau polaire) ; une clé de passage (*passkey*) à 16k aux profondeurs 0.2 et 0.8 trouvée sur les deux modèles. L'expérimentation hors ligne a mesuré le polaire pas meilleur que l'affine à nombre de bits égal |
| `--kv-bits k8v4` | avec `--kv-zones` : la zone centrale quantifiée stocke les clés sur 8 bits et les valeurs sur 4 (13 bits par paire K+V avec facteurs d'échelle de groupe, 0.41× fp16, entre les 0.53× du 8 bits et les 0.28× du 4 bits). `auto` avec `--kv-zones` l'essaie entre 8 et 4 bits. Sur un modèle auquel les zones ne s'appliquent pas (Gemma 4), il s'exécute en 8 bits uniforme. **Expérimental :** `k8v4h` applique également une transformée de Walsh–Hadamard aux valeurs avant la quantification 4 bits (et son inverse à la lecture), afin de répartir les canaux aberrants (*outliers*) ; cette option est strictement volontaire, `auto` ne la choisit jamais. Mesuré avec 8k jetons évalués après un contexte de 8k, perplexité face à `k8v4` : Qwen3-4B 6.568 contre 6.562, Ornith-1.5-9B 4.937 contre 4.920, LFM2.5-8B 8.723 contre 8.750 (une exécution chacun, dans la marge de bruit), et le pic mémoire après une invite de 16k a augmenté d'environ 85 MB sur Ornith et de 30–150 MB sur Qwen3-4B (la copie fp32 des valeurs qu'il fait pivoter). Il fait pivoter les dimensions de tête 2^k et 12·2^k, où la transformée de MLX est sa propre inverse ; les autres dimensions de tête restent non pivotées, et `serve` le journalise au chargement. Cela peut avoir de l'importance sur des contextes plus longs (32k+) ou sur des modèles présentant des canaux aberrants dans V ; cela n'a pas été testé |
| `--kv-zones` | avec `--kv-bits` : conserve les 64 premiers et les 1024 derniers jetons de chaque couche d'attention complète en fp16 et quantifie uniquement les jetons entre eux, au fur et à mesure du pré-remplissage de l'invite. Aucun pré-remplissage fp16 à convertir, l'invite peut donc utiliser tout l'espace quantifié et le pic mémoire diminue ; sur Qwen3-4B, 8k jetons évalués après un contexte de 8k, la perplexité 4 bits est de 6.58 contre 6.56 en fp16 et 8.66 en 4 bits uniforme |
| `--kv-evict F` | **Expérimental**, avec `--kv-zones` : supprime la fraction `F` (0–0.9) de la zone centrale quantifiée de chaque couche d'attention complète à mesure que les jetons quittent la fenêtre récente, en retirant par tête KV ceux dont les clés ont la plus grande norme L2 (arXiv:2406.11430). Ne nécessite aucun poids d'attention, l'attention reste donc sur les noyaux fusionnés ; les puits (*sinks*) et la fenêtre récente ne sont jamais supprimés, et l'espace rapporté par `serve` et `models check` ne compte que les jetons conservés. Après une invite de 16k avec k8v4, le KV sur Qwen3-4B passe de 1.11 GB à 0.89 GB à 0.25 et 0.66 GB à 0.5. Cela a un coût en qualité : perplexité (8k évalués après 8k) 6.71 / 7.04 contre 6.56 sur Qwen3-4B, 9.06 / 9.52 contre 8.75 sur LFM2.5-8B, inchangée sur Ornith-1.5-9B ; une clé de passage à 16k a été perdue à l'une des cinq profondeurs sur Qwen3-4B et Ornith à 0.25, et la sortie gloutonne (*greedy*) diverge du fp16 dès les premiers jetons. Gemma 4, ainsi qu'un modèle qui pré-remplit plus que la fenêtre récente en une passe (vérifié au chargement), conservent chaque jeton et sont dimensionnés en conséquence |
| `--kv-head-split R` | **Expérimental**, incompatible avec `--kv-bits` uniforme : ne conserve le contexte complet que dans la proportion `R` (0.05–1) des têtes KV qui lisent des faits au milieu d'une longue invite, évaluées une fois par modèle sur un jeu synthétique de clés de passage (DuoAttention, mis en cache dans `~/.basalt/head-scores`) ; les autres têtes conservent 128 jetons de puits et 256 jetons récents. Sur Qwen3-4B à 32k avec `R` 0.25 : KV 4.76 → 1.26 GB, décodage 27.2 → 36.2 tok/s, clé de passage 10/10 à 16k et 32k. Refusé, avec un avertissement, sur la famille Qwen3.5 et les hybrides LFM2 / Nemotron-H ainsi que sur les modèles dont l'attention ne passe pas par le cache (Gemma 4). Sur les hybrides, les 25% choisis par ablation ont perdu la clé de passage à 16k (Qwen3.8-27B 0/3 profondeurs, LFM2.5-24B 2/3) et augmenté la perplexité de 24% et 42% ; le choix des têtes par fidélité de sortie correspond à #282. Avec `--kv-zones --kv-bits k8v4` (expérimental, désactivé sauf si les deux sont fournis), les têtes conservées stockent leur long contexte de manière zonée : les 64 premiers et les 1024 derniers jetons exacts, le milieu avec clés sur 8 bits et valeurs sur 4 bits ; les autres têtes restent comme ci-dessus. Comme `--kv-zones`, cela s'applique aux requêtes sans espace de noms de cache d'invite |
| `--prompt-cache-mb N` | mémoire réservée à l'arbre de préfixes du cache d'invite (par défaut : la moitié de ce que l'ensemble de travail GPU recommandé par Metal laisse après les poids, journalisé au chargement ; `0` désactive), voir ci-dessous |
| `--prompt-cache-disk-mb N` | persiste le cache d'invite dans `~/.basalt/prompt-cache/` (`--prompt-cache-dir`) lors d'un arrêt propre, avant un changement de modèle et lorsque `basalt chat` se ferme, afin qu'une session reprise ou un serveur redémarré restaure son préfixe depuis le disque au lieu de le pré-remplir (par défaut `0`, désactivé). Les branches les plus sollicitées sont écrites en premier, jusqu'à `N` MB et uniquement celles dont l'écriture tient dans le délai d'arrêt à un débit supposé de 1 GB/s ; un chemin plus long de la même conversation remplace les fichiers plus courts qu'il recouvre, les fichiers les moins récemment utilisés sont supprimés pour libérer de la place, les fichiers inutilisés depuis `--prompt-cache-disk-days` (7) sont purgés au démarrage, et `basalt sessions prune` effectue la même opération hors ligne. Le répertoire doit être neuf, vide ou être un précédent répertoire de cache d'invite (un répertoire contenant d'autres fichiers est refusé). Un fichier n'est utilisé que par le même modèle (blobs de poids, ou contenu des poids échantillonné hors du cache HF, configuration, tokenizer et modèle de discussion), la même version de basalt et le même format de cache ; tout autre cas, un fichier tronqué ou une disposition de couches différente retombe sur un pré-remplissage normal. Nécessite `--session-log full` (les fichiers contiennent la conversation sous forme de tenseurs KV) et le cache d'invite en mémoire ; `--kv-bits`, `--kv-zones` et les invites multimodales ne sont jamais persistés |
| `--cache-blend` | réutilise les blocs d'invite en cache dans n'importe quel ordre, de manière approximative (CacheBlend) ; `--cache-blend-ratio R` définit la part recalculée (par défaut 0.3), voir ci-dessous |
| `--min-p`, `--top-k`, `--seed` | échantillonnage ; `--seed` rend une exécution non gloutonne reproductible ; le `min_p` d'une requête remplace `--min-p` |
| `--max-tokens` | plafond de génération par défaut (2048–128000) |
| `--dry-run` | vérifie la faisabilité mémoire, puis quitte sans charger |
| `--config basalt.yaml` | options de `serve` depuis un fichier YAML : les clés sous `defaults.{model,serve,mcp}` deviennent les options correspondantes, les options sur la ligne de commande l'emportent, les clés inconnues sont signalées avec ligne et colonne (#344) |
| `--mcp-enable <tool\|group>`, `--mcp-disable <tool\|group>` | avec `--mcp`, active ou désactive sélectivement certains outils ou groupes MCP (`serving`, `gemma`, `media`, `harness`, `xray`, `surgery`, `research`, `all`) sans exposer toute la surface de `--research-tools` ; `--mcp-disable` l'emporte toujours sur `--mcp-enable` et `--research-tools`, et les noms inconnus échouent immédiatement au démarrage. Également `defaults.mcp.enable` / `defaults.mcp.disable` dans `basalt.yaml` (#484) |
| `--adapter name=dir` | charge un adaptateur LoRA mlx-lm sur le modèle de base résident (répétable) ; une requête en sélectionne un avec `X-Basalt-Adapter: name`. Les requêtes sur le même adaptateur s'exécutent ensemble, un changement attend la fin des générations en cours, chaque adaptateur possède son propre espace de noms de cache d'invite ; un adaptateur dont les tenseurs ne correspondent à aucune couche de la base est refusé au démarrage (#179) |
| `--experimental-zero-copy-body` | **Expérimental** : encapsule chaque corps de requête REST dans `Data` sans le copier. Sur Gemma 4 26B-A4B avec 1–8 images, pic d'empreinte mémoire du processus inférieur de 70–95 MB, TTFT inchangé (#345) |
| `--experimental-smallm-kernel` | **Expérimental**, désactivé par défaut (identique à `BASALT_SMALLM_KERNEL=1`) : les passes avant de 4–8 lignes des couches linéaires affines 4 bits (fenêtres de vérification lookup spéculatif et MTP, décodage par lots) passent par le noyau simdgroup-matrix de basalt, qui décode chaque poids une fois pour toutes les lignes. M4 Pro, formes Qwen3.8-27B : 1.5–1.7× le temps d'un jeton pour n'importe quel nombre de lignes entre 4 et 8, là où l'implémentation standard prend 1.7–1.9× à 4 et 3.3–3.7× à 8 ; les sorties diffèrent du standard par l'arrondi bf16, l'identité gloutonne sur des modèles réels reste donc à vérifier (#208) |
| `--experimental-adaptive-thinking-budget` | **Expérimental**, désactivé par défaut : une requête qui ne définit ni `thinking_budget` ni `reasoning_effort` reçoit un budget de réflexion issu d'une estimation de difficulté de son dernier message utilisateur (mots-clés tels que « prove » ou « algorithm », longueur, outils) : facile 512 jetons, moyen 2048, difficile illimité. Uniquement pour les modèles de raisonnement dotés d'une transition de budget (Qwen3.x, LFM2.5) ; non mesuré tant que la passe #41 n'est pas intégrée |
| `--require-verified` | avant le chargement, recalcule le hachage de l'instantané par rapport à ses fichiers compagnons ou aux condensats du Hub et refuse de démarrer sur tout fichier non vérifié (#367) |
| `--port`, `--host` | par défaut 127.0.0.1:8080 ; tout autre hôte nécessite une clé API (`BASALT_API_KEY` ou `--auto-generate-key`) |
| `virtual_keys` (configuration uniquement) | clés API supplémentaires avec leur propre budget cloud : `"virtual_keys": [{"key": "vk-…", "id": "team-a", "max_budget": 2.0}]` dans `~/.gem/config.json` ; une clé comporte au moins 16 caractères, les identifiants et les clés sont uniques ; les dépenses par clé survivent aux redémarrages |
| `--expert-streaming`, `--no-expert-streaming` | diffuse en streaming les poids Mixture-of-Experts routés depuis des fragments safetensors sur SSD (lectures asynchrones par lots `F_NOCACHE` dans des emplacements LRU fixes, `--expert-cache-gb` par défaut à 25% des poids d'experts). Activé automatiquement lorsqu'un point de contrôle `SwitchLinear` empilé local tombe dans le palier `Streaming` (`weights > workingSetBudget` alors que les poids résidents + le cache d'experts tiennent) ; désactiver avec `--no-expert-streaming` ou `BASALT_NO_EXPERT_STREAMING=1` (`--experimental-expert-streaming` reste un alias, #225, #226) |
| `--speech-analyzer` | sert `/v1/audio/transcriptions`, `basalt_transcribe` et l'audio dans `/v1/pipeline` via macOS `SpeechAnalyzer` sur le Neural Engine lorsqu'aucun encodeur audio dédié n'est chargé (alias `--experimental-speech-analyzer`, #222, #226, #230) |
| `--ane-vision-tower DIR` | exécute l'encodeur de vision de PaddleOCR-VL sur le Neural Engine à partir d'un bundle Core AI (`metadata.json` + `tower.aimodel`), en persistant les signets d'artefacts spécialisés et les métadonnées sous `~/.basalt/cache/coreai-vision/` indexés par le SHA-256 du bundle et la build macOS (alias `--experimental-ane-vision-tower`, #224, #226, #400) |
| `--max-concurrent N`, `--max-queue N` | générations en cours de décodage simultanément (par défaut 1 ; chacune détient son propre cache KV) et requêtes en attente d'un emplacement (par défaut 8), par priorité — `basalt chat` d'abord, puis requêtes de service (titres, résumés) et sondes du harnais, puis trafic API, puis benchmarks — et par ordre d'arrivée au sein d'un même niveau ; une requête plus prioritaire trouvant la file pleine écarte celle en attente la moins prioritaire ; au-delà de la file, le serveur répond 503 avec `Retry-After` (un flux ayant déjà envoyé ses en-têtes reçoit un événement d'erreur à la place). Un changement de modèle attend les générations en cours et les nouvelles requêtes font la queue derrière lui ; deux chargements du même modèle n'en font qu'un, un chargement d'un autre modèle pendant ce temps renvoie 503. Sur SIGTERM/SIGINT, les générations disposent de 5 s pour terminer, puis sont annulées afin que le processus quitte |
| `--batch-slots N` | avec `--max-concurrent` à 2 ou plus, jusqu'à N générations décodent ensemble en une passe avant par lots (par défaut 1, désactivé). Prend en charge les couches d'attention complète, d'état récurrent et de fenêtre glissante (Qwen3 dense/MoE, hybrides Qwen3.5/3.6/3.8 et Nemotron-H, LFM2, Gemma 4 : les lignes partagent un anneau de la fenêtre, remplies à gauche et masquées comme les lignes d'attention complète, #255) aussi bien en KV fp16 (`BatchKVCache`) qu'en `--kv-bits` affine uniforme (`4`, `8`, ou même palier `auto` via `BatchQuantizedKVCache`, #243), plus les masques de grammaire `response_format` / outil forcé par ligne ; les requêtes utilisant `--kv-zones`, `k8v4`, `polar4`, `turbo*`, le saut en avant grammatical, le prompt lookup, MTP, CacheBlend ou des pièces jointes multimédias décodent en solo comme auparavant (voir la matrice ci-dessous). Le pré-remplissage et le cache d'invite sont inchangés ; chaque ligne conserve son propre échantillonneur, ses jetons d'arrêt et son `max_tokens`. La sortie gloutonne par lots équivaut au mode solo en qualité, pas au bit près : MLX sélectionne d'autres noyaux pour une ligne que pour plusieurs (multiplication matricielle quantifiée), et une ligne remplie à gauche pour un voisin plus long lit ses clés dans un autre ordre, donc les lignes qui partagent une étape peuvent faire basculer une quasi-égalité (#319). Les lignes qui n'ajoutent aucun remplissage l'une à l'autre laissent leurs logits respectifs inchangés |
| `--session-log full\|meta\|off` | journal de session JSONL local sous `~/.basalt/sessions/<date>/<session>.jsonl` (`0700`/`0600`) : une ligne `request` avant l'appel au moteur et une ligne `response` après (statut, jetons, temps, mémoire, motif d'arrêt) pour chaque point de terminaison, plus des lignes `error` pour les requêtes rejetées (taille uniquement, jamais le corps ni les en-têtes) et `model_switch`. `full` (par défaut) enregistre aussi la conversation et la réponse, `meta` uniquement les tailles et hachages SHA-256 ; `--session-log-dir`, `--session-log-retention-days` (14), `--session-log-max-total-mb` (1024) ; la session est nommée par `X-Basalt-Session` (ou `x-session-id`) ; sans en-tête, une requête qui prolonge une conversation antérieure rejoint sa session et toute autre en démarre une nouvelle. Un identifiant connu s'ajoute à son fichier existant après un redémarrage du serveur (`session_resume`), et une session inactive pendant `--session-idle-minutes` (30) est suspendue. `basalt sessions list \| show <id\|latest> \| stats <id\|latest>` lit les fichiers sans charger de modèle ; `basalt chat` conserve un historique multi-tours dans sa propre session et `basalt chat --resume <id\|latest>` le reprend (pas pour les sessions `meta`). **Réutilisation du cache d'invite.** Le serveur conserve le cache KV du modèle pour les invites récentes dans un arbre de préfixes : les invites qui commencent par les mêmes jetons partagent une seule copie stockée de ce début, et une requête ne pré-remplit que ce qui suit le plus long préfixe stocké. Ainsi, le tour suivant d'une conversation ne coûte que ses nouveaux jetons (un résultat d'outil ajouté à une longue transcription d'agent, et non tout l'historique à nouveau), et une deuxième conversation qui s'ouvre avec le même message système et les mêmes outils — un sous-agent Claude Code, un autre fil Codex — repart de la partie partagée au lieu de la pré-remplir à nouveau. La correspondance se fait par jetons, aucun identifiant de conversation n'est donc nécessaire (`prompt_cache_key`, `metadata.user_id` et `x-session-id` sont ignorés) ; un client qui souhaite isoler ses invites envoie `X-Basalt-Cache-Key: <name>` (1-256 octets, sur chaque point de terminaison de génération) et obtient son propre arbre, qui partage le budget en octets mais aucun préfixe avec l'arbre partagé ni avec d'autres clés ; les requêtes de titre et autres requêtes de service ne touchent jamais au cache. Sous le budget `--prompt-cache-mb`, la branche la moins récemment utilisée est coupée à partir de son extrémité (la branche d'instantané d'un modèle hybride, voir ci-dessous, est supprimée en entier, car son état récurrent n'est valide qu'à son extrémité), de sorte qu'une conversation inactive conserve le plus longtemps son invite système et ses outils, et le nœud jusqu'auquel une requête en cours réutilise n'est jamais évincé (pour un modèle hybride, il s'agit de son nœud d'instantané ; la requête possède sa propre copie des données, donc l'éviction du reste de sa branche ne peut pas l'affecter) ; l'arbre conserve également au plus 4096 branches, en supprimant au-delà la branche libre la moins récemment utilisée. Les statistiques d'utilisation rapportent ce qui a réellement été réutilisé : `prompt_tokens_details.cached_tokens` (Chat Completions), `input_tokens_details.cached_tokens` (Responses), `cache_read_input_tokens` (Anthropic, où `input_tokens` ne compte que le reste pré-rempli). Les modèles hybrides attention/SSM tels que Qwen3.5/3.6 et Ornith-1.5, ainsi que Gemma 4 avec ses couches à fenêtre glissante, réutilisent eux aussi le tour précédent d'une conversation : leur état récurrent ou rotatif ne peut pas être rembobiné, donc pendant le pré-remplissage d'une invite le serveur en conserve un instantané à la fin du texte de la requête, avant les jetons de fermeture du modèle de discussion, et le tour suivant qui prolonge ce texte restaure l'instantané et ne pré-remplit que ce qui suit (Ornith-1.5-9B, invite d'agent de 12.6k jetons : le deuxième tour prend environ 1 s au lieu d'environ 36 s). Un tour réutilisé peut différer d'une exécution sans cache après ses premiers jetons : le pré-remplissage est découpé différemment, ce qui décale légèrement les résultats bf16 (mesuré sur Ornith : l'état restauré est identique bit à bit à un pré-remplissage depuis zéro découpé aux mêmes endroits, et diffère d'un pré-remplissage en une phase d'au plus 1.56 sur les logits de la dernière position avec le même top 5 ; sur Gemma 4 12B, le cache restauré est également identique bit à bit, et sur une session de douze tours d'environ ~4k jetons il diffère d'un pré-remplissage en une phase de 0.60–2.33 avec le même jeton glouton, à peu près autant qu'un pré-remplissage en une phase par blocs de 256 jetons au lieu de 512 diffère de lui-même, 2.53, de sorte qu'à température 0 un jeton presque à égalité peut encore basculer). Ils ne réutilisent qu'à partir d'un tel instantané, donc une deuxième conversation avec la même invite système est pré-remplie en entier. `--kv-bits` pré-remplit toujours l'invite complète.

**CacheBlend (optionnel, approximatif).** L'arbre de préfixes n'aide que lorsqu'une invite commence de la même manière ; un agent qui colle les mêmes fichiers dans un autre ordre les pré-remplit tous à nouveau. `--cache-blend` conserve également le KV de chaque bloc d'invite — un bloc se termine après chaque ligne vide, que le tokenizer l'écrive en un jeton ou en deux jetons de saut de ligne, de sorte que les fichiers et messages séparés par des lignes vides conservent leurs propres blocs ; les blocs de moins de 16 jetons sont toujours recalculés — et réutilise un bloc où qu'il se trouve dans une invite ultérieure (les clés sont stockées avant RoPE et pivotées vers la nouvelle position). Les blocs en cache ont été calculés à côté d'un autre texte, leur KV est donc obsolète : suivant CacheBlend (arXiv:2405.16444), la première couche est recalculée pour chaque jeton, et seule la fraction `--cache-blend-ratio` des jetons réutilisés (par défaut 0.3), plus chaque jeton absent du magasin, sont recalculés sur les couches suivantes. Le budget va d'abord aux 32 premiers jetons de chaque bloc réutilisé, dont le contexte a le plus changé lorsque le bloc a été déplacé (comme dans EPIC, arXiv:2410.15332), classés selon l'écart de leur KV sur la deuxième couche, et ensuite seulement aux jetons les plus divergents du reste. La passe avant fusionnée (*blended*) coûte environ 1.2× le propre pré-remplissage du modèle par jeton recalculé, si bien qu'une invite n'est fusionnée que lorsque (1 − ratio) × la part de jetons réutilisés vaut au moins 0.2, et tant que l'ensemble du cache reste dans la limite de 16 384 jetons ; autrement — une nouvelle invite, peu de réutilisation, `--cache-blend-ratio 1`, un contexte long — elle emprunte le pré-remplissage par blocs natif du modèle et ses blocs sont stockés depuis ce cache (les clés sont dé-pivotées depuis post-RoPE, exactes à l'arrondi du dtype du cache près, ~2⁻⁸ relatif en bf16). Le résultat est approximatif. Mesuré sur Qwen3-4B-4bit (M4 Pro) avec six fichiers figés de 550–900 jetons (`benchmarks/cacheblend`) dans quatre nouveaux ordres, chacun accompagné d'une nouvelle question (4 854 des ~5 066 jetons issus de blocs), en évaluant la réponse gloutonne du pré-remplissage complet (50 jetons) sous *teacher forcing* — log-probabilité moyenne des jetons de référence et accord top-1 par position, sur cet échantillon de 200 positions (0.01 représente deux positions) :

| cache | log-prob | top-1 | perplexité |
|---|---|---|---|
| pré-remplissage complet | −0.094 | 0.995 | 1.099 |
| ratio 0 | −0.180 | 0.925 | 1.198 |
| ratio 0.15 (la valeur de l'article) | −0.166 | 0.945 | 1.181 |
| **ratio 0.3 (par défaut)** | −0.123 | 0.960 | 1.131 |
| ratio 0.5 | −0.125 | 0.970 | 1.134 |
| ratio 1 (pré-remplissage natif) | −0.094 | 0.995 | 1.099 |

Recalculer d'abord les débuts de blocs est ce qui fait de 0.3 la valeur par défaut : avec l'écart de couche 1 seul, un ratio de 0.3 laissait un écart de perplexité de 0.085 et même 0.5 laissait 0.038 ; avec les débuts de blocs d'abord, 0.3 laisse 0.032 (0.50 : 0.035). Sur quatre autres ordres et questions sur les mêmes fichiers, l'écart est plus grand (0.096 à 0.3, contre 0.169 sans débuts de blocs et 0.120 pour l'ancienne valeur par défaut 0.5), la borne de 0.05 tient donc sur l'échantillon de référence, pas sur toute invite. `--cache-blend-ratio 0` sacrifie la qualité au profit du pré-remplissage le plus court. Uniquement les modèles denses des familles Llama et Qwen3 ; les autres modèles conservent le chemin de préfixe exact. Avec l'option activée, le budget du cache d'invite est partagé en deux entre l'arbre et le magasin de blocs. `cached_tokens` ne compte toujours que les jetons exacts de l'arbre de préfixes ; les jetons fusionnés sont comptés dans `prompt_tokens` et journalisés (`[CacheBlend] Blended N prompt tokens: R from cached chunks, X of them recomputed`), et l'arbre ne stocke que la tête exacte d'une invite fusionnée. Une passe fusionnée maintient brièvement en mémoire le cache assemblé ainsi que les clés et valeurs non pivotées des blocs en même temps (environ deux fois le KV de l'invite, par ex. ~5 GB pour 16k jetons de Qwen3-4B), ce que les estimations mémoire n'incluent pas. Aux faibles ratios, le coût fixe des couches 0–1 et de la passe d'écart domine, de sorte que 0.15 et 0.3 sont plus lents que ne le suggère le modèle de coût linéaire. Désactivé par défaut car il modifie les sorties ; `--prompt-cache-mb 0` le désactive également.

Confidentialité : tous les clients partagent un seul arbre de préfixes, et `cached_tokens` révèle combien de jetons initiaux une invite partage avec des invites antérieures, un appelant peut donc sonder ce qu'un autre client a envoyé. Sur un serveur partagé par des personnes qui ne doivent pas voir les invites les unes des autres, exécutez avec `--prompt-cache-mb 0` ; avec `--cache-blend`, le temps jusqu'au premier jeton montre aussi quels blocs un autre client a envoyés.
