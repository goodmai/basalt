# Команды

> Languages: [English](../../commands.md) · **Русский** · [中文](../zh/commands.md) · [Español](../es/commands.md) · [Français](../fr/commands.md) · [日本語](../ja/commands.md) · [Deutsch](../de/commands.md) · [한국어](../ko/commands.md) · [Bahasa Indonesia](../id/commands.md)

`basalt` без подкоманды запускает `chat`.

| Команда | Назначение |
|---|---|
| `basalt onboard` | мастер первого запуска: подбирает модель под вашу машину и скачивает её |
| `basalt fit` | считывает характеристики оборудования и ранжирует каталог моделей относительно них |
| `basalt chat --model <id>` | интерактивный чат в терминале |
| `basalt serve --model <id> --rest` | REST-сервер на порту :8080 (совместимый с OpenAI и Anthropic) |
| `basalt serve --model <id> --mcp` | MCP stdio-сервер для Claude Desktop / Cursor |
| `basalt serve --model <id> --stats` | выводит телеметрию в stderr каждые 5 s (`--stats-interval`); те же метрики доступны по `GET /api/v1/stats` и в MCP `status` |
| `basalt serve --model <id> --canary-minutes 30` | каждые 30 мин, в периоды простоя, отправляет один тестовый запрос с известным ответом с фоновым приоритетом; счётчики прохождений/ошибок, вырожденных ответов и дрейфа tok/s и доли принятых черновиков (draft acceptance) по каждой модели доступны в разделе `health` эндпоинта `GET /api/v1/stats` (#325) |
| `basalt models list --author <org>` | просмотр моделей указанного автора на HuggingFace |
| `basalt models download <repo-id>` | скачивание в общий кэш HF |
| `basalt models info <repo-id>` | размер, квантование, контекстное окно |
| `basalt models cache` | что хранится на диске и сколько места занимает |
| `basalt models check <repo-id>` | поместится ли модель в память (ненулевой код возврата, если не поместится) |
| `basalt models check --deep <repo-id>` | дополнительно, ещё до скачивания: загружает только заголовки safetensors (несколько сотен КБ), строит по ним скелет модели только по формам тензоров и рендерит шаблон чата (chat template); перечисляет отсутствующие, лишние или несовпадающие по форме тензоры, неподдерживаемый `model_type` или ошибку шаблона и завершается с ненулевым кодом |
| `basalt models inspect <repo-id>` | проверяет целостность закэшированной модели и измеряет её реальную битность |
| `basalt models inspect --verify <repo-id>` | также пересчитывает хеш каждого закэшированного файла и сверяет его с sidecar-файлом или дайджестом Hub: `true`, `false` или `unknown` для каждого файла, только чтение (#367) |
| `basalt models distill <model> --prompts FILE --teacher-url URL --teacher-model NAME` | дистиллирует модель-учителя за API в формате OpenAI или Anthropic (`--provider`) в LoRA-адаптер для локальной модели; ключ берётся из `BASALT_TEACHER_API_KEY` вместе с `BASALT_TEACHER_URL`; `--budget-usd` останавливает процесс до превышения лимита расходов, `--filter verify` оставляет только ответы, совпадающие с `answer` промпта, `--on-policy` заставляет модель-ученика сэмплировать, пока учитель basalt с тем же токенизатором оценивает её токены на `/v1/score` (потокенный обратный KL), офлайн-прогоны сохраняют контрольные точки каждые `--checkpoint-every` шагов и возобновляются через `--resume` (#393) |
| `basalt models train-jepa <model> --dataset FILE` | обучает JEPA LoRA-адаптер и проектор на мультивидовом датасете (одна сцена на строку JSONL, минимум два ракурса); выводит loss и ранг эмбеддингов до и после обучения |
| `basalt models convert <source> --out DIR` | Универсальный конвертер «любой в любой» (#546): переквантование между `--to macaq:affine|mxfp4|moe` (блочное преобразование Уолша–Адамара + доработка переворотом знаков по гессиану, взвешенный по роутеру 2.8 bpw MoE #599), `--to flatquant` / `--to lirquant` (#594), `--to sinq` / `a-sinq` / `eaquant` (#561), `--to e8p` (2-битная решётка `QuIP#` + `TurboBoA` Babai–LLL, #589), `--experimental-qtip 2.0\|2.5\|3.0` (#494), `nf4`, `SVD-LLM V2` / `OBR` (#592), нативные i-quants `.gguf` и `MACaQ-R`, а также `--pv-tune` (`--pv-preset fast|full`, #545), предметно-ориентированная доработка QAT STE и постквантовый аудит качества/справедливости/утечек (`#623`). Также доступно через REST `/v1/models/convert*` и в macOS-приложении через `ConvertModelSheet` |
| `basalt serve --video-model <id> --rest` | Запускает поэтапную Video Studio для 24 GB UMA (`LTX-2.5 AV-DiT`, `Kandinsky 6.0`, `LingBot-Video MoE`, `Wan 2.2`) поверх `/v1/videos/*` с каузальным 3D-VAE, Metal-ядром STA и мультиплексированием `.mp4` через `AVAssetWriter` (#608–#611, #614) |
| `basalt review --diff FILE\|- --model <id>` | ревью diff на локальной модели; `--gitlab` / `--gitea URL --repo R --number N` вместо этого загружают merge request, `--post` публикует ревью обратно (`GITLAB_TOKEN` / `GITEA_TOKEN`) (#35) |
| `basalt compose` | запускает, планирует, сравнивает (`diff`), вытягивает (`pull`) или останавливает многомодельную YAML-систему (`models`, `pipeline`, `pipelines`, `experimental`, `mcp`, `variables`, `profiles`); горячо перезагружает модели, пайплайны, бюджеты и живые настройки `experimental` (`speech_analyzer`, `image_fallback`, `telemetry_confidence_every`, `adaptive_thinking_budget`) через `/v1/compose/apply` (#412, #423, #485) |
| `basalt cloud configure` | настройка облачного резерва OpenRouter для задач, не помещающихся локально |
| `basalt cloud cost` | текущие расходы на облачный резерв |

Внутри `basalt chat`:

| Ввод | Действие |
|---|---|
| `/clear` | очистить диалог и экран |
| `/color`, `/theme` | переключить цветовую тему терминала |
| `exit`, `quit` | выйти (без слэша) |

Флаги `serve`, о которых стоит знать:

| Флаг | Зачем он нужен |
|---|---|
| `--reasoning-effort none` | запрещает рассуждающей модели тратить весь бюджет токенов внутри `<think>` |
| `--reasoning-effort xhigh\|medium\|low` | бюджет размышлений для семейства Qwen |
| `--quant 4bit` | выбор подкаталога с квантованием в репозиториях, где поставляется несколько вариантов |
| `--kv-bits 4\|8\|auto` | квантование KV-кэша — освобождает память под генерацию на машинах с ограниченной RAM; отключает переиспользование prompt-кэша. MLX выполняет prefill промпта в fp16 и квантует его после, поэтому сам промпт не может быть длиннее, чем в fp16 (даже короче: во время конвертации кратковременно хранятся обе копии). `auto` остаётся в fp16 с переиспользованием prompt-кэша, пока промпт запроса плюс `max_tokens` помещаются в память, а если нет — запускает этот запрос в 8 битах, иначе в 4 |
| `--kv-bits turbo3\|turbo4\|turbo8v4` | **Экспериментальный** (#471): кэш TurboQuant из этого форка на слоях полного внимания (вращение, кодовая книга Ллойда–Макса, норма на вектор; первые два и последние два подходящих слоя остаются в 8-битном аффинном виде). Несовместим с `--kv-zones`. Замеры на M4 Pro при контексте 8k относительно 4-битного аффинного кэша: декодирование на 8–13% медленнее (Qwen3.8-27B: 13.8 против 15.0 tok/s, LFM2.5-24B: 82 против 94); перплексия декодирования на 384 токенах +0.3% / +1.3% против +1.5% для 4-bit на Qwen3.8, +10.1% / +3.6% против +5.0% на LFM2.5; KV на 16k не меньше (Qwen3.8: 460 / 511 MB против 461, LFM2.5: 118 / 131 против 97, Gemma 4 26B-A4B: 423 против 306). Сжатие применяется на этапе декодирования: многотокенный чанк читает сырые ключи |
| `--kv-bits polar4` | **Экспериментальный** (#351), совместно с `--kv-zones`: квантованная середина зоны хранит каждую RoPE-пару ключа в одном байте (5 бит фазы, 3 бита модуля по квантилям Рэлея, масштабированным по каждой голове и паре по первому батчу миграции), а остальные размерности — в 4-битном аффинном виде; значения (values) остаются в 4-битном аффинном виде. Только для Qwen3, Qwen3.5 и LFM2, у которых RoPE объединяет размерности i и i + d/2; любая другая модель оставляет аффинные ключи и пишет об этом в лог. Замеры на M4 Pro, 256 токенов декодирования после 8k, в сравнении с зонированным q4 и k8v4: перплексия Qwen3.8-27B 8.61 против 8.56 / 8.50, LFM2.5-24B 61.2 против 76.5 / 70.9 (шумная выборка в 256 токенов); зонированный KV 196 против 197 / 255 MB и 59 против 62 / 80 MB; декодирование 12.4 против 14.0 / 14.6 tok/s и 11.3 против 19.5 / 18.2 (середина декодируется в fp16 на каждом шаге, полярного ядра нет); 16k passkey на глубинах 0.2 и 0.8 найден на обеих моделях. Офлайн-исследование показало, что при равной битности polar не лучше аффинного квантования |
| `--kv-bits k8v4` | совместно с `--kv-zones`: квантованная середина хранит ключи в 8 битах, а значения в 4 (13 бит на пару K+V с групповыми масштабами, 0.41× fp16 — между 0.53× у 8-битного и 0.28× у 4-битного). Режим `auto` с `--kv-zones` пробует его между 8 и 4 битами. На модели, к которой зоны не применимы (Gemma 4), работает как равномерный 8-битный кэш. **Экспериментально:** `k8v4h` дополнительно применяет преобразование Уолша–Адамара к значениям перед 4-битным квантованием (и обратное при чтении), чтобы размазать выбросы по каналам; включается только явно, `auto` его никогда не выбирает. Замеры с оценкой 8k токенов после 8k контекста, перплексия против `k8v4`: Qwen3-4B 6.568 против 6.562, Ornith-1.5-9B 4.937 против 4.920, LFM2.5-8B 8.723 против 8.750 (по одному прогону, в пределах шума), а пиковое потребление памяти после промпта 16k выросло примерно на 85 MB на Ornith и на 30–150 MB на Qwen3-4B (из-за fp32-копии вращаемых значений). Вращает головы размерностей 2^k и 12·2^k, где преобразование MLX совпадает со своим обратным; остальные размерности голов остаются без вращения, о чём `serve` сообщает при загрузке. Может иметь значение на более длинных контекстах (32k+) или на моделях с выбросами каналов в V; это не проверялось |
| `--kv-zones` | совместно с `--kv-bits`: удерживает первые 64 и последние 1024 токена каждого слоя полного внимания в fp16 и квантует только токены между ними по мере prefill промпта. Нет промежуточного fp16 prefill для последующей конвертации, поэтому промпт может занять весь объём квантованной памяти, а пик памяти падает; на Qwen3-4B при оценке 8k токенов после 8k контекста перплексия при 4 битах составляет 6.58 против 6.56 у fp16 и 8.66 у равномерного 4-битного кэша |
| `--kv-evict F` | **Экспериментальный**, совместно с `--kv-zones`: отбрасывает долю `F` (0–0.9) квантованной середины каждого слоя полного внимания по мере выхода токенов из недавнего окна — на каждую KV-голову те токены, чьи ключи имеют наибольшую норму L2 (arXiv:2406.11430). Не требует весов внимания, поэтому внимание остаётся на свёрнутых (fused) ядрах; sink-токены и недавнее окно никогда не вытесняются, а доступный объём, о котором сообщают `serve` и `models check`, учитывает только сохраняемые токены. После промпта 16k с k8v4 размер KV на Qwen3-4B снижается с 1.11 GB до 0.89 GB при 0.25 и до 0.66 GB при 0.5. Это ухудшает качество: перплексия (8k после 8k) 6.71 / 7.04 против 6.56 на Qwen3-4B, 9.06 / 9.52 против 8.75 на LFM2.5-8B, без изменений на Ornith-1.5-9B; 16k passkey был потерян на одной из пяти глубин на Qwen3-4B и Ornith при 0.25, а жадный вывод расходится с fp16 уже на первых токенах. Gemma 4 и модели, выполняющие prefill объёмом больше недавнего окна за один проход (проверяется при загрузке), сохраняют все токены и оцениваются соответствующим образом |
| `--kv-head-split R` | **Экспериментальный**, несовместим с равномерным `--kv-bits`: хранит полный контекст только в доле `R` (0.05–1) KV-голов, которые извлекают факты из середины длинного промпта — оценка выполняется один раз для модели на синтетическом наборе passkey (DuoAttention, кэшируется в `~/.basalt/head-scores`); остальные головы хранят 128 sink-токенов и 256 недавних токенов. На Qwen3-4B на 32k с `R` 0.25: KV 4.76 → 1.26 GB, декодирование 27.2 → 36.2 tok/s, passkey 10/10 на 16k и 32k. Отклоняется с предупреждением на гибридах семейства Qwen3.5 и LFM2 / Nemotron-H, а также на моделях, чьё внимание не проходит через этот кэш (Gemma 4). На гибридах выбранные абляцией 25% теряли passkey на 16k (Qwen3.8-27B 0/3 глубин, LFM2.5-24B 2/3) и повышали перплексию на 24% и 42%; выбор голов по точности выхода (output fidelity) отслеживается в #282. С `--kv-zones --kv-bits k8v4` (экспериментально, отключено, если не заданы оба флага) сохранённые головы хранят длинный контекст зонированно: точные первые 64 и последние 1024 токена, середина с 8-битными ключами и 4-битными значениями; остальные головы работают как описано выше. Как и `--kv-zones`, применяется к запросам без пространства имён prompt-кэша |
| `--prompt-cache-mb N` | память, выделенная под префиксное дерево prompt-кэша (по умолчанию: половина от того, что остаётся в рекомендуемом Metal рабочем наборе GPU после весов, выводится в лог при загрузке; `0` отключает), см. ниже |
| `--prompt-cache-disk-mb N` | сохраняет prompt-кэш на диск в `~/.basalt/prompt-cache/` (`--prompt-cache-dir`) при корректном завершении работы, перед сменой модели и при выходе из `basalt chat`, чтобы возобновлённая сессия или перезапущенный сервер восстанавливали префикс с диска вместо повторного prefill (по умолчанию `0`, выключено). Первыми записываются самые горячие ветки в пределах `N` MB и только те, запись которых укладывается в таймаут завершения при расчётной скорости 1 GB/s; более длинный путь того же диалога заменяет более короткие файлы, которые он покрывает, наименее недавно использованные файлы удаляются для освобождения места, файлы, не использовавшиеся `--prompt-cache-disk-days` (7) дней, удаляются при старте, а `basalt sessions prune` делает то же самое офлайн. Каталог должен быть новым, пустым или прежним каталогом prompt-кэша (каталог с посторонними файлами отклоняется). Файл используется только той же самой моделью (блобы весов или сэмплированное содержимое весов вне кэша HF, конфиг, токенизатор и шаблон чата), той же версией basalt и форматом кэша; всё остальное, усечённый файл или иная раскладка слоёв приводят к обычному prefill. Требует `--session-log full` (файлы хранят диалог в виде KV-тензоров) и включённый prompt-кэш в памяти; `--kv-bits`, `--kv-zones` и мультимодальные промпты никогда не сохраняются на диск |
| `--cache-blend` | переиспользует закэшированные чанки промпта в произвольном порядке приближённо (CacheBlend); `--cache-blend-ratio R` задаёт пересчитываемую долю (по умолчанию 0.3), см. ниже |
| `--min-p`, `--top-k`, `--seed` | параметры сэмплирования; `--seed` делает не-жадный прогон воспроизводимым; `min_p` в запросе переопределяет `--min-p` |
| `--max-tokens` | потолок генерации по умолчанию (2048–128000) |
| `--dry-run` | проверка осуществимости по памяти с последующим выходом без загрузки |
| `--config basalt.yaml` | параметры `serve` из YAML-файла: ключи в `defaults.{model,serve,mcp}` преобразуются в соответствующие флаги, флаги командной строки имеют приоритет, неизвестные ключи выводятся с указанием строки и столбца (#344) |
| `--mcp-enable <tool\|group>`, `--mcp-disable <tool\|group>` | совместно с `--mcp` выборочно включает или отключает отдельные MCP-инструменты или группы (`serving`, `gemma`, `media`, `harness`, `xray`, `surgery`, `research`, `all`) без раскрытия всей поверхности `--research-tools`; `--mcp-disable` всегда имеет приоритет над `--mcp-enable` и `--research-tools`, а неизвестные имена сразу вызывают ошибку при запуске. Также `defaults.mcp.enable` / `defaults.mcp.disable` в `basalt.yaml` (#484) |
| `--adapter name=dir` | загружает LoRA-адаптер mlx-lm поверх резидентной базовой модели (можно указывать несколько раз); запрос выбирает его через `X-Basalt-Adapter: name`. Запросы с одним и тем же адаптером выполняются вместе, переключение дожидается активных генераций, у каждого адаптера собственное пространство имён prompt-кэша; адаптер, чьи тензоры не подходят ни к одному слою базы, отклоняется при старте (#179) |
| `--experimental-zero-copy-body` | **Экспериментальный**: оборачивает тело каждого REST-запроса в `Data` без копирования. На Gemma 4 26B-A4B с 1–8 изображениями пиковый объём памяти процесса ниже на 70–95 MB, TTFT не улучшается (#345) |
| `--experimental-smallm-kernel` | **Экспериментальный**, по умолчанию выключен (то же, что `BASALT_SMALLM_KERNEL=1`): прямые проходы по 4–8 строкам 4-битных аффинных линейных слоёв (окна проверки speculative-lookup и MTP, батчевое декодирование) выполняются через simdgroup-matrix ядро basalt, которое декодирует каждый вес один раз для всех строк. На M4 Pro и формах Qwen3.8-27B: 1.5–1.7× от времени одного токена на любом числе строк 4–8, тогда как штатный код даёт 1.7–1.9× на 4 и 3.3–3.7× на 8; выходы отличаются от штатных на величину округления bf16, поэтому побитовая/жадная идентичность на реальных моделях ещё не проверена (#208) |
| `--experimental-adaptive-thinking-budget` | **Экспериментальный**, по умолчанию выключен: запрос, не задающий ни `thinking_budget`, ни `reasoning_effort`, получает бюджет размышлений по оценке сложности последнего пользовательского сообщения (ключевые слова вроде "prove" или "algorithm", длина, инструменты): лёгкий — 512 токенов, средний — 2048, сложный — без ограничения. **Переиспользование prompt-кэша.** Сервер хранит KV-кэш модели для недавних промптов в префиксном дереве: промпты, начинающиеся с одинаковых токенов, разделяют одну сохранённую копию этого начала, и запрос выполняет prefill только для хвоста после самого длинного сохранённого префикса. Поэтому следующий ход диалога стоит лишь своих новых токенов (результат инструмента, добавленный к длинному транскрипту агента, не требует пересчёта всей истории), а второй диалог, открывающийся тем же системным промптом и инструментами — субагент Claude Code, другой поток Codex — стартует с общей части вместо её повторного prefill. Сопоставление идёт по токенам, поэтому идентификатор диалога не нужен (`prompt_cache_key`, `metadata.user_id` и `x-session-id` игнорируются); клиент, который хочет изолировать свои промпты, передаёт `X-Basalt-Cache-Key: <name>` (1–256 байт на любом эндпоинте генерации) и получает собственное дерево, которое делит бюджет в байтах, но не имеет общих префиксов с общим деревом или другими ключами; генерация заголовков и прочие служебные запросы кэш никогда не затрагивают. В рамках бюджета `--prompt-cache-mb` наименее недавно использованная ветка подрезается с конца (ветка со снимком гибридной модели, см. ниже, удаляется целиком, поскольку её рекуррентное состояние валидно только в конце), поэтому простаивающий диалог дольше всего удерживает системный промпт и инструменты, а узел, до которого переиспользует кэш выполняющийся запрос, никогда не вытесняется (для гибридной модели это её узел снимка; у запроса есть собственная копия данных, так что вытеснение остальной части ветки на него не влияет); дерево также хранит не более 4096 веток, удаляя сверх этого наименее недавно использованную свободную ветку. Поля `usage` отражают реально переиспользованное количество: `prompt_tokens_details.cached_tokens` (Chat Completions), `input_tokens_details.cached_tokens` (Responses), `cache_read_input_tokens` (Anthropic, где `input_tokens` учитывает только довычисленный остаток). Гибридные модели attention/SSM, такие как Qwen3.5/3.6 и Ornith-1.5, а также Gemma 4 со слоями скользящего окна, тоже переиспользуют предыдущий ход диалога: их рекуррентное или вращающееся состояние нельзя откатить назад, поэтому при prefill промпта сервер сохраняет его снимок в конце текста запроса, перед закрывающими токенами шаблона чата, и следующий ход, расширяющий этот текст, восстанавливает снимок и выполняет prefill только для продолжения (Ornith-1.5-9B, агентский промпт на 12.6k токенов: второй ход занимает около 1 s вместо примерно 36 s). Переиспользованный ход может отличаться от некэшированного прогона после первых токенов: prefill разбивается на чанки иначе, что слегка сдвигает результаты bf16 (замерено на Ornith: восстановленное состояние побитово равно prefill с нуля, разрезанному в тех же точках, и отличается от однофазного prefill максимум на 1.56 в логитах последней позиции при том же top 5; на Gemma 4 12B восстановленный кэш тоже побитово равен, а за сессию из двенадцати ходов ~4k токенов отличается от однофазного prefill на 0.60–2.33 при том же жадном токене — примерно настолько же, насколько однофазный prefill чанками по 256 вместо 512 токенов отличается от самого себя, 2.53, так что при temperature 0 близкий к ничьей токен всё же может переключиться). Они переиспользуют кэш только от такого снимка, поэтому второй диалог с тем же системным промптом проходит prefill полностью. `--kv-bits` всегда выполняет prefill всего промпта.

**CacheBlend (опционально, приближённо).** Префиксное дерево помогает лишь тогда, когда промпт начинается одинаково; агент, вставляющий те же файлы в другом порядке, заново прогоняет prefill для всех них. `--cache-blend` дополнительно сохраняет KV каждого чанка промпта — чанк заканчивается после каждой пустой строки, независимо от того, записывает ли её токенизатор как один токен или как два токена перевода строки, так что файлы и сообщения, разделённые пустыми строками, сохраняют собственные чанки; чанки короче 16 токенов всегда пересчитываются — и переиспользует чанк в любом месте более позднего промпта (ключи хранятся до RoPE и поворачиваются на новую позицию). Закэшированные чанки вычислялись рядом с другим текстом, поэтому их KV устарел: следуя CacheBlend (arXiv:2405.16444), первый слой пересчитывается для всех токенов, а на последующих слоях пересчитывается только доля `--cache-blend-ratio` от переиспользованных токенов (по умолчанию 0.3) плюс все токены, отсутствующие в хранилище. Бюджет в первую очередь идёт на первые 32 токена каждого переиспользованного чанка, чей контекст при переносе изменился сильнее всего (как в EPIC, arXiv:2410.15332), ранжированные по величине отклонения их KV на втором слое, и лишь затем на наиболее отклоняющиеся токены из остальной части. Смешанный прямой проход стоит около 1.2× собственного prefill модели на пересчитанный токен, поэтому смешивание применяется только когда (1 − ratio) × доля переиспользованных токенов составляет не менее 0.2 и пока весь кэш укладывается в 16 384 токена; в противном случае — свежий промпт, мало переиспользования, `--cache-blend-ratio 1`, длинный контекст — используется штатный чанковый prefill модели, а чанки сохраняются из этого кэша (ключи развращаются обратно из post-RoPE с точностью до округления dtype кэша, ~2⁻⁸ относительной погрешности в bf16). Результат является приближённым. Замерено на Qwen3-4B-4bit (M4 Pro) на шести фиксированных файлах по 550–900 токенов (`benchmarks/cacheblend`) в четырёх новых перестановках, каждая с новым вопросом (4 854 из ~5 066 токенов из чанков), с оценкой жадного ответа полного prefill (50 токенов) в режиме teacher forcing — средний log-prob эталонных токенов и совпадение top-1 по позициям на этой выборке из 200 позиций (0.01 соответствует двум позициям):

| кэш | log-prob | top-1 | перплексия |
|---|---|---|---|
| full prefill | −0.094 | 0.995 | 1.099 |
| ratio 0 | −0.180 | 0.925 | 1.198 |
| ratio 0.15 (значение из статьи) | −0.166 | 0.945 | 1.181 |
| **ratio 0.3 (по умолчанию)** | −0.123 | 0.960 | 1.131 |
| ratio 0.5 | −0.125 | 0.970 | 1.134 |
| ratio 1 (нативный prefill) | −0.094 | 0.995 | 1.099 |

Именно первоочередной пересчёт голов чанков делает 0.3 значением по умолчанию: при одном только отклонении 1-го слоя ratio 0.3 оставлял разрыв по перплексии 0.085 и даже 0.5 оставлял 0.038; с приоритетом голов чанков 0.3 оставляет 0.032 (0.50: 0.035). На четырёх других перестановках и вопросах по тем же файлам разрыв больше (0.096 при 0.3 против 0.169 без голов чанков и 0.120 для старого значения по умолчанию 0.5), поэтому граница 0.05 выполняется на бенчмарк-выборке, а не на каждом промпте. `--cache-blend-ratio 0` меняет качество на максимально короткий prefill. Работает только на плотных моделях семейств Llama и Qwen3; остальные модели идут по точному префиксному пути. При включённом флаге бюджет prompt-кэша делится пополам между деревом и хранилищем чанков. `cached_tokens` по-прежнему считает только точные токены префиксного дерева; смешанные токены учитываются в `prompt_tokens` и выводятся в лог (`[CacheBlend] Blended N prompt tokens: R from cached chunks, X of them recomputed`), а дерево сохраняет только точную голову смешанного промпта. Смешанный проход кратковременно удерживает в памяти одновременно собранный кэш и неповёрнутые ключи и значения чанков (примерно вдвое больше KV промпта, например ~5 GB для 16k токенов Qwen3-4B), чего оценки памяти не учитывают. При малых значениях ratio доминируют фиксированные затраты слоёв 0–1 и прохода оценки отклонений, поэтому 0.15 и 0.3 работают медленнее, чем предсказывает линейная модель затрат. По умолчанию выключен, так как меняет выходы; `--prompt-cache-mb 0` также его отключает.

Приватность: все клиенты делят одно префиксное дерево, и `cached_tokens` раскрывает, сколько начальных токенов промпт разделяет с предыдущими промптами, так что вызывающий может прозондировать, что отправлял другой клиент. На сервере, которым пользуются люди, не должные видеть промпты друг друга, запускайте его с `--prompt-cache-mb 0`; при `--cache-blend` время до первого токена также выдаёт, какие чанки отправлял другой клиент.
